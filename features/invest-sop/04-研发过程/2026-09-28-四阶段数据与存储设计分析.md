# 四阶段信息与数据组成及存储实现分析

> **研发过程记录（2026-09-28）**
> 产生于 invest-sop 需求规格 grilling 定稿后的设计推导问答，作为 02-设计规格 的前置输入。
> 标注口径：**【已定】** = 需求规格 + grilling 裁决锁定；**【提案】** = 本文推导（表名/拆表方式/存储形态），设计规格定稿前的候选方案。
> 上游：[需求规格说明](../01-需求规格/需求规格说明.md)、[设计思路与产品功能讲解](2026-09-28-设计思路与产品功能讲解.md)。

## 一、总述：双轨存储 + 三类容器

### 1.1 核心判断：结构化与否，决定存哪、谁来管

规格的裁决逻辑是「**结构化才可被纪律检查与复盘消费**」（澄清 #12）+「**联动单向引用**」（F08：journal/wiki 记 projectId，项目域不反向持有）。由此推出双轨：

| 轨 | 内容 | 容器 | 判据 |
|---|---|---|---|
| **数据轨（结构化）** | 状态、谓词、数值、枚举、留痕 | `domain/research` 新表（Flyway V2 起） | 需要**机器消费**：状态机流转、纪律检查纯函数、证伪命中检测、复盘自动计算 |
| **信息轨（非结构化）** | 叙述、笔记、讨论过程、知识沉淀 | 既有 journal / wiki / 会话历史 | 只需要**人读**：研究叙述、备忘、方法论、结论沉淀 |

### 1.2 三类容器（全部有先例）

1. **新建 `domain/research` 一族表**【已定方向，schema 是提案】：结构化数据轨。
2. **既有 `journal_entry` / `wiki_entry` 加 `project_id` 引用列**【已定，列明进 F04 迁移范围】：非结构化承接 + 单向引用（照 `trade_id` 软引用先例：无 FK、不级联）。
3. **会话历史（conversation/chat_message，ADR-0011 服务端 stateStore）**【已定】：Skill 引导过程与未保存草稿的临时家园——**不落项目库**，用户显式确认保存才进数据轨。

## 二、分述：逐阶段的信息与数据组成

### 阶段① 新分析（发现标的、立项研究）

| 类别 | 组成 | 存储实现 |
|---|---|---|
| **数据** | 项目主干：标的代码/名称/行业、当前阶段枚举、归属 userId | 【已定字段语义】【提案表】`research_project` |
| | 四阶段完成度：每阶段三态 + 完成方式角标（必备产物齐套→AUTO / 手动→MANUAL） | 【提案】`research_stage_record` 子表（或项目表内嵌，设计规格定） |
| | 新分析 checklist：F01「必须有」清单映射的勾选项（公司基本面清单/行业框架/估值方法适配，F05 模板带入） | 【提案】阶段产物表，勾选项为行（F01 内容运行时定义，不能定死列） |
| **信息** | 研究笔记正文、立项理由叙述 | journal `RESEARCH_NOTE` 类型 + `project_id`（既有类型，天然契合） |
| | Skill 引导对话中的草稿（未保存） | 会话历史（不自动暂存） |
| | 值得沉淀的行业认知 | wiki `RESEARCH_NOTE` 类型 + `project_id`（M13 既有类型，零扩展成本） |

**要点**：立项入口（筛选器一键 / 对话引导）只写 `research_project` + 预填字段；watchlist 零自动联动。

### 阶段② 制定投资策略

| 类别 | 组成 | 存储实现 |
|---|---|---|
| **数据** | 五字段中的结构化部分：**估值区间**（下限/上限两个数值列，校验下<上，手动填写）、**仓位计划**（目标占比等数值）、**买入条件**（结构化条目） | 【已定字段】【提案表】`research_strategy_doc`（1:1 挂项目） |
| | **证伪条件**【已定口径】：价格/估值两类**结构化谓词**（类型：跌破价格/升破价格/PE 超阈/PB 超阈 + 阈值 + 方向）+ 事件类人工勾选项（布尔 + 文本） | 【提案】`research_falsifier` 子表——**必须独立成行**，F15 命中检测要逐条查询判定 |
| | 策略状态机：DRAFT / FINALIZED **两级**（覆盖式，无版本链）+ 定稿时间戳（定稿是显式动作、进入下一阶段语义） | `research_strategy_doc` 状态列 |
| **信息** | **投资逻辑**（长文本，本质是叙述）、风险叙述 | 策略文档内的文本列（字段属于策略，不外置 journal） |
| | 策略推演过程讨论 | 会话历史；结论性沉淀走 journal/wiki |

**要点**：估值区间**不自动派生**默认证伪条件——两份数据各自显式，Skill 只做引导建议。

### 阶段③ 建仓与持仓

| 类别 | 组成 | 存储实现 |
|---|---|---|
| **数据** | **建仓计划**（F09）：分批方案（每批价格区间/数量/金额/预计占比）+ 凯利参数（胜率/赔率，**v1 手动输入**）+ 占比合计校验 | 【提案】`research_entry_plan` + `research_entry_batch` 子表 |
| | **纪律检查留痕**（F10/F12，NFR-2 只增不改）：时间、检查类型（买入/加/减/卖出）、命中项快照（规则、阈值、当时值）、结论（确认/**越过**）、**越过理由（必填）** | 【提案】`research_check_record` **append-only 表**——只 INSERT，domain 层不提供更新用例（是否加 DB 层触发器兜底，设计规格定） |
| | **证伪命中记录**（F15）：命中条件、依据数据与口径、命中时间、状态（待评审/已评审） | 【提案】`research_falsifier_hit`，外链评审记录 |
| | 消费的规则 | **不复制**——运行时读 M13 `principle_rule`（每用户每指标至多一条，UNIQUE 兜底） |
| | 实际持仓/成交 | **不存储**——以 portfolio 流水为唯一真源（计划 ≠ 成交，F09 既定） |
| | 情报订阅关联（F11） | M15 交付后挂接（顺延项），v1 无表 |
| **信息** | 持仓期间备忘（公告反应、临时判断） | journal `BUY_MEMO`/`SELL_MEMO` + `project_id` |
| | 情报原文/新闻流 | M15 `domain/research-intel`（未交付） |
| | 项目事件流（立项/流转/定稿/检查/证伪评审） | 【已定】application 层在用例点写入 journal 时间线：`TimelineEventType` 扩展 + `timeline()` 合并改造 |

### 阶段④ 复盘

| 类别 | 组成 | 存储实现 |
|---|---|---|
| **数据** | **复盘记录**（F13）：模板档位（月主/季深/周简）、期间、维度结构化作答（决策质量/结果质量/纪律遵守度/归因——**最小字段集待 MS-24 内容评审**） | 【提案】`research_review` + 作答子表（字段集未定，作答宜行式或 JSONB，设计规格定） |
| | **自动带入快照**（F14）：买卖点 vs 后续走势、区间收益的计算值 + **口径标注**（区间起止、价格口径）+ 用户覆盖值 | 复盘记录内成对列（auto_value / overridden_value + 口径列）；**快照式存储**——不复算历史，写入时定格 |
| | **归因圈选**：自动时间窗圈定的交易集合 + 手动修正 | 复盘记录关联选中的 trade id 集合（软引用） |
| | **证伪评审记录**（F15）：结论枚举（维持/减仓/退出/修订策略）+ 理由 + 处置 | 【提案】`research_falsifier_review`，append-only 留痕 |
| | **回流状态**（F16）：待确认/已回流 + 目标 wiki 条目引用 | 复盘记录上的状态列 + 软引用 |
| | 模板改进建议：建议内容 + 对应阶段 + 来源复盘（F16 结构化沉淀） | 【提案】`research_feedback`（只收集不生效） |
| **信息** | 复盘正文叙述（归因分析、经验总结） | 复盘记录文本列 |
| | 回流的知识结论 | wiki_entry（扩展类型还是复用 `RESEARCH_NOTE`，**延迟至设计规格**） |

## 三、跨阶段存储约定（全部有仓库先例，设计规格直接继承）

1. **归属隔离**：所有新表带 `user_id`，非本人访问 404（照 journal/会话先例）【已定】。
2. **乐观锁**：聚合根表加 `version` 列（V9 给 5 张聚合表加 version 的先例）【提案，沿惯例】。
3. **软引用**：跨域关联（`project_id`、trade 引用）无 FK、不级联，删除项目解除关联不删内容【已定 F08】。
4. **留痕不可篡改**：`research_check_record` / `research_falsifier_review` 只增不改【已定 NFR-2】；与「策略可修订（覆盖式两级）」是两类数据，边界清晰。
5. **迁移**：单一 V2 迁移承接全部新表 + 两张既有表加列（`journal_entry`/`wiki_entry`）+ 回填策略【已定走 Flyway，接基线后 V2 起】。
6. **读写路径**：domain 纯 POJO + `infrastructure/persistence` 的 `*JpaEntity` + 仓库实现（`ddl-auto: none`，schema 全归 Flyway）——照既有七个域的装配模式。

## 四、ER 草图（提案）

```
research_project ──1:N── research_stage_record        （四阶段完成度）
      │ 1:1
      research_strategy_doc ──1:N── research_falsifier （证伪谓词/事件项）
      │ 1:N
      research_entry_plan ──1:N── research_entry_batch （分批）
      │ 1:N
      research_check_record      （append-only 检查留痕）
      research_review ──┬── 作答/快照/归因圈选
      research_falsifier_hit ──→ research_falsifier_review （命中→评审）
      research_feedback          （模板改进建议）

journal_entry (+project_id)  ←─ 单向软引用（备忘/研究笔记/时间线事件）
wiki_entry   (+project_id)   ←─ 单向软引用（知识沉淀）
principle_rule (M13)         ←─ 运行时只读消费，不复制
trade (portfolio)            ←─ 复盘归因软引用，不复制
conversation (ADR-0011)      ←─ 会话态草稿，不落项目库
```

## 五、收束

数据轨（research 族表）存「机器要消费的」——状态、谓词、数值、留痕；信息轨（journal/wiki/会话）存「人要读的」——叙述与知识；两轨靠单向 `project_id` 软引用缝合，复用既有容器到「加一列」的程度，新域只造机器消费所需的表。表名与拆表方式属【提案】，是 02-设计规格 的主体。
