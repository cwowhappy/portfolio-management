## 二、经验（做对了什么）

1. **独立终审的拦截力再次验证**：执行期全绿的 mock 单测完全没拦住「刻度放大 100 倍」——审查者沿「服务层产出 → 展示层消费」全链路追刻度才发现。fixture 与服务层真实产出形态不一致 = 测试在验证一个不存在的世界。
2. **计划代码对照真实代码核实的红利仍在**：F10 匹配面（`TemplateView` 无风险等级 → 改 `RiskProfile.recommendedWeights`）与 `AllocationSliceCategory` 两值假设纠正都发生在计划期/实现早期，避免了错误架构落库；**但签名核实覆盖不了数值刻度**——`ratio()` 签名对了、`part/total×100` 的刻度没看（见不足 #1）。
3. **e2e 失败快照（error-context.md）是断言设计的实证工具**：具名渲染器接管工具卡（标签不显示）这一前端机制，靠快照而非猜测定位，断言改到真实渲染产物（表格标题/降级卡）后一次通过。
4. **对 LLM 自由度的工程化收束**：真 LLM e2e 需要 `test.setTimeout(240s)`（18 参工具生成慢）；smoke 指令必须显式点名工具名 +「只用内置工具」（否则 LLM 顺手调 MCP `sw_daily` 触发 HITL 审批挂起、无最终文本）。

## 三、不足

1. **「数值刻度」不在计划核实清单内**：对照真实代码核实的清单只有签名/类型/包名——`ratio()` 的百分数刻度、`RiskProfile` 权重「和为 100」注释都在源码里，但没人去看。10 项终审发现中 4 项由此而生。
2. **计划期算术与文案笔误偏多**：3 处亿元换算错（2.1E12 算成 2100 亿）、摘要文案两处不一致、「三档」风险画像（实为五档，规格期没读 `RiskProfile` 全文）——计划自审查签名不查数值。
3. **对真实 LLM 行为的两轮试错**：e2e 断言信号错选、smoke MCP 分流挂起——本可在写用例前先看一次真实对话快照再定断言。

## 四、优化建议

1. **「服务层数值刻度」写入契约文档与计划核实清单**：`PortfolioApplicationService.ratio`（百分数）、`RiskProfile.recommendedWeights`（和为 100）、`DeviationView.deviation`（百分点）在服务层 Javadoc 固化一行刻度说明；计划期核实清单从「签名/类型」扩到「签名/类型/数值刻度」。
2. **展示层用例的 fixture 必须取服务层真实产出形态**（百分数而非小数）——可在 02 规范测试节加一句，属 C5/G9 同类的 checklist 条目化。
3. 真 LLM 用例（e2e/smoke）先抓一次对话快照再写断言（本次 240s 超时与「只用内置工具」两条经验可直接入 `docs/technology/modules/01-Agent实现.md` 的冒烟节）。
