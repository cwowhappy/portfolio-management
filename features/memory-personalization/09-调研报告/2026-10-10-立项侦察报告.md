## 一、长期记忆链路现状（M18-F01 的对象）

### 1.1 记忆不在数据库——是工作区 Markdown 文件

- Flyway V1~V6 无任何 memory 表（grep `memory` 零命中）；无 JPA 实体/Repository。
- 实际磁盘布局（已验证存在，全仓约 260+ 用户目录）：
  - `backend/.agentscope/workspace/<userId>/MEMORY.md` —— 策展层（LLM consolidation 维护的去重汇总）
  - `backend/.agentscope/workspace/<userId>/memory/YYYY-MM-DD.md` —— append-only 日账本（每 flush 一节，节标题带时间戳）
- 条目结构 = **纯 Markdown 文本，无任何结构化字段**（无分类/标签/置信度列）。日账本实测形态：`## Memory Flush — <ISO8601>` 节 + bullet 要点。
- 保留策略：日账本 90 天后归档 `memory/archive/`，session 日志 180 天剪除（jar 内 `MemoryConfig.java:53-58` 常量 + `MemoryMaintenanceMiddleware`）。

### 1.2 记忆装配与写入触发（全部在 agentscope-harness 2.0.3 库内，仓库自有代码零参与）

- 装配点 `agent/HarnessAgentFactory.java:54-84`（`build(Long userId)`）：`.memory(MemoryConfig.builder().flushTrigger(throttled(flushMinGap)).build())`（:75-77）——**只覆写 flush 触发策略**（`invest.mcp.harness.memory.flush-min-gap` 缺省 30 分钟，`InvestProperties.java:388-392`、`application.yml:141-142`）；flush/consolidation prompt、模型、token 上限、保留期全走 harness 缺省。
- **库契约（jar sources 实证）——单一写入者约束**：
  - 日账本 **只由 `MemoryFlushManager` 写**（"daily ledger written ONLY by this class"）；
  - `MEMORY.md` **只由 `MemoryConsolidator` 写**（"MEMORY.md written ONLY by MemoryConsolidator"，周期把日账本合并去重，上限 `consolidationMaxTokens=4000`）；
  - `MemorySaveTool`（`memory_save` 工具）是 "the only sanctioned entry point for the agent to write long-term memories"——同时 append `MEMORY.md` 与当日账本。
- 写入触发四条路径：
  1. 每轮调用后 flush（节流 30 分钟，主模型按 `DEFAULT_FLUSH_PROMPT` 英文抽取提示词从对话窗口抽取要点追加日账本）——jar 内 `MemoryFlushMiddleware`；
  2. 压缩前 flush（`flushBeforeCompact=true`，compaction trigger 30 条消息 / keep 10，`HarnessAgentFactory.java:70-74`）；
  3. 周期 consolidation（缺省 `consolidationMinGap=30m`）——日账本 → `MEMORY.md`；
  4. LLM 主动写工具 `memory_save`（`HarnessAgentFactory` 未调 `disableMemoryTools()`，记忆工具与 hook 全开）。
- **外部直写文件的后果**：技术上可 append（文件在工作区磁盘），但违反单一写入者契约——consolidation 周期重写 `MEMORY.md` 会把外部写入/手工编辑内容合并掉或冲掉。

### 1.3 记忆读取路径（Agent 每轮怎么消费）

- **全量注入，非检索**：jar 内 `WorkspaceContextMiddleware.onSystemPrompt`（`WorkspaceContextMiddleware.java:200-213`）在静态系统提示后追加 `<loaded_context>`，其中 `<memory_context>` = `MEMORY.md` 全文（token 预算截断，超限提示用 memory_search 取旧条目）。**每轮每次调用重读重注入**。
- 按需检索：`memory_search`（关键词扫描，无向量检索，覆盖 `MEMORY.md`+`memory/*.md`）/ `memory_get`（取行）。
- 日账本不进系统提示，只能经 memory_search/memory_get 到达。

### 1.4 三套存储互不相同（勿混淆）

| 存储 | 位置 | 用途 |
|---|---|---|
| Agent 会话态 stateStore | `.agentscope/state/<userId>/<sessionId>/agent_state.json`（`JsonFileAgentStateStore`，`HarnessAgentFactory.java:69`） | 模型上下文消息序列（含压缩摘要） |
| 长期记忆 | `workspace/<userId>/MEMORY.md` + `memory/*.md` | 跨会话画像/事实 |
| 前端对话历史（DB） | `conversation` / `chat_message`（V1:35-53，含 payload JSONB） | 前端会话列表/消息回显，与 Agent 上下文两套 |

## 八、立项张力点汇总（事实推导，供拍板）

1. **M18-F01 管理界面的存储通道**：记忆是库管的 Markdown 文件，库契约单一写入者（flush/consolidator/memory_save）——「编辑/删除」若直写文件，会被周期 consolidation 冲掉或合并；且条目无结构化字段，「逐条管理」需要解析约定。选项空间：文件直读写（对抗库契约）/ DB 投影镜像（管理面操作 DB，需定与文件层的同步关系）/ 只经 sanctioned 通道（append+标记）等。
2. **M18-F01 与 M18-F03 的写通道同构**：事件摘要写记忆与用户编辑记忆面对同一个「谁是合法写入者」问题——两功能点宜共用一套裁决。
3. **M18-F02 注入通道**：静态 TEXT 被 prompt_asset_version hash 钉住；skill 先例 = 中间件追加（`<available_skills>`），画像注入可仿（新追加段）或改 build 时动态拼接——版本链口径需处理。
4. **M18-F02 画像源二义**：「关注行业/股票」有两份源（industry_watch vs intelligence_subscription），立项拍板取哪份（或合并口径）。
5. **M18-F02 token 成本**：每轮全量注入（memory 现状即每轮注入 MEMORY.md）——画像注入的「按需」语义（哪些数据、何时、多大预算）需定义。
6. **M18-F03 触发模式**：同步 hook（事务内 publishEvent 先例，但事务边界风险）/ 事务后（零先例，需引入）/ 定时批量摘要（先例全套：IntelligenceChatPort + EvalScheduler 模板 + timeline 读路径现成；系统 key 无冲突）。
7. **ArchUnit 落位约束**：记忆文件 IO 端口若给 application/web 用，须定义在 domain 或 application（infrastructure 不能实现 agent 包接口）；画像组装可落 agent 包（application 通配白名单已覆盖）。
