## 二、执行注记（评审链拦截择要）

13 任务 subagent-driven（B0 探针 + B1~B6 后端 + F1~F4 前端 + E1 e2e + C1 收口），逐任务独立审查全过；关键拦截项：

1. **两处计划-规格矛盾评审期裁决**：B2（`editCuratedLine` 返 void vs 设计规格 `CuratedMutationResult`——以 brief 为准，规格 §2.2 回填消歧）；B6 ⚠️（游标「仅全成功推进」vs「批完成即推进」内部矛盾——以 brief 红线为准，规格 §4.1 回填消歧）。两处均属「计划冻结时规格旧文未同步」，靠逐任务评审对读拦下，未流到实现。
2. **B6 key 缺席批前门承重核实**：`IntelligenceChatPort` 无 key 返回 empty 与调用失败同形——若无批前门，首跑即「全 empty 假成功」推进游标造成永久漏摘要；调度器批前 `DEEPSEEK_API_KEY` 缺席整批快退为承重路径（非装饰），评审专项核实其测试锚。
3. **E1 评审发现 F4 有意变更引入的 e2e 回归**：F4 把删除确认改为 `window.confirm`，破坏既有 `conversation.spec.ts`（无 dialog handler 时 Playwright 点击即崩）——实现者自查未见，评审以独立证据链确认，C1 补 `page.once("dialog", accept)` 收口。跨任务副作用必须靠 e2e 全量回归兜底。
4. **终审 With fixes（2 Important + 4 Minor）**：Important×2 = 503-IO 映射未兑现（`UncheckedIOException` 落 500，违背规格 §2.2 与端口 javadoc 承诺）/ portfolio 两裸模态使 roadmap「P3⑤ 全量真清零」失真；修复波 7 项全收口（503 handler + MockMvc、两模态接 `useDialogA11y` + vitest、游标语义四处文本、B2 并发 javadoc 收窄 + 规格风险注记、keepalive 传输层失败归因「内容过长」、notice 随 reload 成文、本复盘）。
