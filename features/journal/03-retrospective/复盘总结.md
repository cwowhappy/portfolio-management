## 二、经验（做对了什么）

1. **subagent-driven + 双重评审拦住了约 8 处计划缺陷**——这些缺陷全部是「凭记忆写代码样例」而非「读真实代码」导致的；若单人直接落地会全部上线（详见「附：计划缺陷清单」）。
2. **领域层真正做到了 TDD 红→绿**（P1 每个任务先写失败测试再实现），评审会核实 RED/GREEN 证据、不轻信实现者报告。
3. **越权隔离被最终评审独立确认**——`tradeId` 归属校验（trade→position→portfolio→user 多跳）是真正安全的，不是表面功夫。

## 三、不足

1. **计划质量是最大短板**：约 8 处缺陷全部源于「写计划时没读真实代码，凭记忆/类比 allocation 范式」。
2. **评审派发误写**：「`JournalEntryView` 16 字段」是协调者误写，导致评审报假 Critical、多花一轮裁决。
3. **非严格 TDD**：服务/控制器是「先实现、后补单测」（Task 2 实现 → Task 4 单测），继承 allocation 范式，非严格 red-first。
4. **前端组件覆盖失衡**：`EntryEditor`/`EntryList`/`JournalBoard` 三个组件 0% 覆盖，靠整体 90.26% 掩盖（计划只给 TimelineView 配了组件测试）。
5. **模型选择保守**：全程 sonnet，机械「抄代码 + 跑测试」任务本可用 haiku 省成本。
6. **e2e 未能全绿**：完整套件有既有隔离 flakiness（`registerAndApprove` 对「注册成功」的脆弱断言 + 共享 dev DB），未被提前识别。

## 四、优化建议

1. **写计划前必须读真实代码**：涉及既有域类/测试基座/前端模式时，先 `Read` 真实文件核对签名，别类比（本次返工最大单一根因）。
2. **加「计划校验」环节**：writing-plans 后派只读子代理，把计划代码样例对照代码库校验签名/模式。
3. **服务/控制器也走 red-first**：把「实现」和「单测」合并进同一任务，而非拆成两个任务做 test-after。
4. **前端每个组件配测试**：组件级 0% 覆盖作为计划内硬约束，不满足于整体覆盖率达标。
5. **模型分层**：机械抄写用 haiku、集成/判断用 sonnet、最终评审用 opus。
6. **反代 query 透传作为固定 checklist**：route handler 一律带 `new URL(req.url).search`，路由测试必测 query 透传。
7. **e2e 隔离修复单独立项**：`registerAndApprove` 改稳断言 + 共享 DB 隔离，不混进功能里程碑。
