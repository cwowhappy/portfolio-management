## 四、飞书平台能力核实（全部对照官方文档，2026-09-27）

### 4.1 两种接入模式对比

| 维度 | 群自定义机器人（webhook） | 企业自建应用（bot） |
|---|---|---|
| 接入成本 | 群设置加机器人拿 webhook URL，零开发前置 | 开放平台建应用+开机器人能力+申请权限+发版本（自审） |
| 消息类型 | text/post/image/share_chat/interactive 卡片（**无 markdown**） | 同左 + 视频/音频/文件/表情包等全量 |
| 发送方向 | **只能发**，收不到任何消息/回调（官方明文） | 双向：发消息 API + 事件订阅收消息 |
| 卡片按钮 | 仅跳转 URL，**无回调交互** | 支持回调（长连接模式下也可用） |
| 频率限制 | **100 条/分钟 + 5 条/秒**（单租户单机器人） | App 维度 50 次/秒 + 1000 次/分钟；单用户/单群 5 QPS |
| @指定人 | 支持（`<at user_id="ou_xxx">`），但机器人自身无法查询 open_id | 支持，可用通讯录 API 查 |
| 安全机制 | 关键词(≤10)/IP 白名单(≤10)/HMAC-SHA256 签名（时间差>1h 拒绝） | app_id/app_secret → tenant_access_token（≤2h，SDK 自动管理） |
| 部署要求 | 出站 HTTPS 即可 | 发消息：出站 HTTPS；收事件：公网回调 URL **或 WebSocket 长连接**（仅自建应用支持） |

来源：[自定义机器人使用指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[企业自建应用开发流程](https://open.feishu.cn/document/develop-process/self-built-application-development-process)、[发送消息](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/create)、[频控策略](https://open.feishu.cn/document/server-docs/api-call-guide/frequency-control)

### 4.2 关键机制细节

- **webhook 签名**：以 `timestamp + "\n" + secret` 为 key，对**空 body** 做 HmacSHA256，Base64 后随 `timestamp`/`sign` 字段提交——JDK/Python 标准库即可，零依赖。
- **长连接模式**（收事件+卡片回调）：飞书 SDK 内置 WebSocket，**仅需出站**、无需公网入站；建连时鉴权一次，后续事件明文推送（Encrypt Key/Verification Token 不适用）；每应用 ≤50 连接；集群模式不广播（多实例仅随机一个收到）；事件须 **3 秒内**处理完成否则重推。来源：[使用长连接接收事件](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration-case)、[处理卡片回调](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/handle-card-callbacks)
- **发布审核**：自建应用免飞书官方审核，变更走"创建版本→申请发布→**企业管理员审核**"——本人即管理员，可自审通过；测试版应用免发布自动生效。来源：[发布与审核自建应用](https://open.feishu.cn/document/home/intro-to-custom-app-review)
- **收消息权限**：单聊 `im:message.p2p_msg`；群 @机器人 `im:message.group_at_msg`（对应事件 `im.message.receive_v1`）。来源：[接收消息事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive)

## 五、方案比选

| | **A：混合双通道（选定 ✅）** | B：自建应用统一出口 | C：极简先行 |
|---|---|---|---|
| 结构 | collector 告警→群机器人 webhook；backend 预警+对话→自建应用 | 全部经自建应用；collector 告警打 backend 转发端点 | P0 全走群机器人；对话后置 |
| 告警链路独立性 | ✅ backend 挂了告警照发 | ❌ 依赖 backend 存活（被监控方依赖反模式） | ✅ |
| 凭证/模板 | 两套凭证、Python/Java 各一份格式化 | 单一凭证、单一模板 | 一套，但 P2 时预警模板要迁移 |
| 见效速度 | P0 一期内即有价值 | 需先建自建应用+转发端点 | 最快 |
| 对话支撑 | ✅ P2 自然演进 | ✅ | 后置重来 |

**选定 A 的核心理由**：① 告警链路与被监控方解耦（backend 故障时 collector 告警仍可达——真实可用性收益，方案 B 做不到）；② 告警量极低，群机器人 100 条/分钟富余两个数量级；③ 自建应用凭证只在 backend 出现一次，不扩散到 collector；④ 对话场景反正要建自建应用，S2 蹭同一套，无额外成本。

## 六、总体架构（方案 A）

### 6.1 通道一：群自定义机器人（collector，S1）

```
runner 终态/patrol findings → FeishuAlerter（格式适配 + 签名）→ POST 群 webhook → 飞书群卡片
```

- `collector/scheduler/alerts.py` 新增 `FeishuAlerter`：**复用** `WebhookAlerter` 的重试/退避/吞错语义（组合或继承），新增内部事件 → 飞书卡片（`msg_type=interactive`，正文含任务名/状态/错误摘要/@本人）的格式转换；`alerter_from_env()` 识别飞书专用 env 构造。
- 配置：`FEISHU_BOT_WEBHOOK` + `FEISHU_BOT_SECRET`（签名校验，opt-in 语义与现状一致：未配置静默）。`COLLECTOR_ALERT_WEBHOOK` 保留（通用逃生通道不动）。
- 改动面：collector 单模块 + `.env.example`/docker-compose env 透传 + README 环境变量表（顺带补 `COLLECTOR_ALERT_WEBHOOK` 存量缺口）。

### 6.2 通道二：企业自建应用（backend，S2+S3）

```
S2: @Scheduled 日终巡检 → PrincipleRule×持仓估值评估 → FeishuClient 发卡片（im/v1/messages）
S3: ws 长连接 im.message.receive_v1 → open_id 白名单 → HarnessAgent → 回复消息
```

- **依赖**：`com.larksuite.oapi:oapi-sdk`（发消息+长连接）；`agentscope-extensions-channel-feishu` 待 P2 spike 通过后引入（不通过则手工桥接）。
- **落位（DDD/ArchUnit 合规）**：`infrastructure/im/` 新子包（`FeishuClient`：token 管理+发消息，参照 `infrastructure/market/` 的 HttpExecutor 范式做限流+重试）；预警评估逻辑在 domain/application 层（与 wiki 域 PrincipleRule 协作）；S3 对话桥接挂 `agent/`。
- **配置**：`InvestProperties` 新增一组（如 `invest.im.*`：app-id/app-secret/owner-open-id/告警 chat_id）；env 注入沿用现状（明文 env 是既有惯例，P1-10 加密设施落地后统一收纳）。
- **调度**：backend 引入 `@EnableScheduling` + `@Scheduled`（Spring 原生，成本一个配置类；巡检时点定在 collector 日终数据就绪后，如 18:00，具体时序见 §八 风险 9）。
- **S3 关键设计**：3 秒事件时限 vs LLM 响应——收到事件即 ack，会话处理异步化，按 `message_id` 幂等去重（应对重推）；对话入口白名单仅 owner open_id（单用户模型）。

### 6.3 数据流时序（交易日日终）

```
17:30 collector freshness_patrol ──→ 通道一：飞书群「新鲜度巡检」卡片
~18:00 backend 原则预警巡检 ──→ 通道二：飞书「原则预警」卡片（超限规则×持仓）
任意时刻 用户在飞书发消息 ──→ 通道二：ws 事件 → HarnessAgent → 回复
```

| 4 | 部署环境对 `open.feishu.cn` 出站连通性（历史有 WAF 拒答先例：push2.eastmoney） | 通道不可用 | P0 前置：部署机 curl webhook 探测 |
| 5 | webhook 请求体上限（官方 20KB/30KB 两说，保守按 20KB） | 巡检滞留清单过长被拒 | 卡片正文截断+「N 项滞留，详见系统」汇总策略 |
| 6 | 凭证明文 env（群机器人 secret、app_secret） | 泄露面 | 沿用现状惯例+开启签名校验；P1-10（MCP token 加密）落地后统一收纳 |
| 7 | backend 首次引入调度设施 | 新基础设施维护面 | 仅 `@EnableScheduling`+一个 cron 配置项，保持最小 |
| 8 | 长连接集群不广播 | 未来多实例部署时事件只到一个实例 | 当前单实例部署无影响；文档记录，多实例化时再议 |
| 9 | 原则预警巡检时序依赖 collector 日终数据就绪（估值/PE/PB 数据源口径待定） | 巡检结果失真或依赖不满足 | P1 需求规格阶段确认：巡检取数走 backend 行情缓存直算还是消费 collector 日表 |
| 10 | MS-15 验收措辞与计划联动 | 文档口径漂移 | §九 更新清单随 P1 交付执行 |
