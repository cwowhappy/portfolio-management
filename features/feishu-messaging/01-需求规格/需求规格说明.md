# 飞书即时通信（feishu-messaging）需求规格说明

- **版本**：v1.0（2026-09-27，brainstorming 阶段产出，用户已确认）
- **关联**：[可行性方案](../09-调研报告/2026-09-27-飞书即时通信可行性方案.md)（平台能力核实、方案比选、风险清单的完整论证均在该报告，本规格不重复）｜里程碑挂接 MS-15（原则预警载体）+ M14 系统与工程（采集告警增强）+ M03 对话式投研问答（IM 入口扩展）
- **实施节奏**：P0（通道一·采集告警）→ P1（通道二·原则预警）→ P2（通道二·飞书对话）；每期独立交付

## 一、背景与目标

**现状**：系统唯一主动外发通道是 collector 通用 webhook 告警（P0-2，`collector/collector/scheduler/alerts.py`——opt-in、尽力而为），payload 为内部事件 dict，直连飞书需格式适配；backend 无任何通知与调度设施；投资原则预警（MS-15）无载体，SMTP 引入仍"⏳ 待决策"（`docs/plans/2026-08-27-产品落地计划.md:325`）。

**目标**：以飞书为即时通信载体，交付三个场景——

| 场景 | 内容 | 期 |
|---|---|---|
| S1 采集告警推送 | 任务终态 failed/partial + 日终新鲜度巡检结果 → 飞书群卡片 | P0 |
| S2 投资原则预警 | PrincipleRule 四类阈值（单票仓位/单行业仓位/PE/PB）日终巡检超限 → 飞书卡片 | P1 |
| S3 飞书内对话 | 飞书单聊查询持仓/行情、与 HarnessAgent 对话 | P2 |

**架构定案**（方案 A 混合双通道，比选论证见可行性报告 §五）：S1 走群自定义机器人 webhook（collector 直发，**backend 挂了也能告警**）；S2+S3 走企业自建应用（oapi-sdk 长连接，免公网入站，凭证只在 backend 出现）。

## 二、需求澄清汇总（决策表，均经用户确认）

| # | 议题 | 决定 |
|---|---|---|
| 1 | 场景范围 | S1+S2+S3；**不含**账户类通知（邮箱验证/找回密码）替代邮件——SMTP 决策独立 |
| 2 | 用户模型 | 单用户（本人）；open_id/白名单进配置，**不建**飞书↔系统账号绑定表 |
| 3 | 飞书侧条件 | 已有组织且本人是管理员（自建应用免官方审核、可自审发布） |
| 4 | 预警触发时机 | 日终定时巡检（不做交易时实时拦截） |
| 5 | 架构 | 方案 A 混合双通道（collector 群机器人 + backend 自建应用） |
| 6 | 分期 | P0 告警 → P1 预警 → P2 对话（spike 关卡在前） |

## 三、功能需求

### A. 通道一：群机器人采集告警（P0）

- **FR-A1 飞书告警器**：`alerts.py` 新增 `FeishuAlerter`（继承/组合 `WebhookAlerter`，复用其重试退避与吞错语义），把两类内部事件转为飞书 `msg_type=interactive` 卡片：`task_run` → 标题「采集任务告警」，`failed` 红色/`partial` 橙色头部，lark_md 正文含任务名/状态/模式/错误/消息；`freshness_patrol` → 标题「数据新鲜度巡检」橙色头部，正文含日期/滞留项明细。
- **FR-A2 签名校验**：配置 `FEISHU_BOT_SECRET` 时启用官方签名算法（`timestamp + "\n" + secret` 为 key 对空 body 做 HmacSHA256 再 Base64，随请求带 `timestamp`/`sign`）；未配置则不带。
- **FR-A3 装配与优先级**：`alerter_from_env()` 识别 `FEISHU_BOT_WEBHOOK` → `FeishuAlerter`；其次 `COLLECTOR_ALERT_WEBHOOK` → 现状 `WebhookAlerter`（保留为通用逃生通道）；两者皆未配置 → None（现状路径）。**runner.py/jobs.py 零改动**（装配点 `jobs.py:420` 签名不变）。
- **FR-A4 正文健壮性**：error/message 字段超长截断；巡检滞留清单最多列 8 项、超出以「共 N 项」汇总，整体消息体控制在飞书 20KB 保守线内。

### B. 通道二：自建应用原则预警（P1）

- **FR-B1 应用开通**：开发者后台建自建应用 + 机器人能力 + `im:message` 发消息权限 + 发布（本人自审）；建告警群并拉入机器人，取 chat_id。
- **FR-B2 FeishuClient**：backend `infrastructure/im/` 新子包——tenant_access_token 管理（≤2h 有效期刷新）+ 发消息 API 封装，参照行情域 `HttpExecutor` 的「限流+可重试」范式；ArchUnit 分包守卫内落位。
- **FR-B3 原则预警巡检**：backend 引入 `@EnableScheduling` + `@Scheduled`（首次引入调度设施，保持最小），交易日日终（collector 数据就绪后，时点待设计规格定）评估 PrincipleRule×持仓估值，超限项经 FeishuClient 发卡片；规则停用（enabled=false）不推。
- **FR-B4 配置组**：`InvestProperties` 新增 `invest.im.*`（app-id/app-secret/owner-open-id/chat-id），env 注入沿用现状惯例。

### C. 通道二：飞书对话（P2）

- **FR-C1 spike 关卡**：先验证 `agentscope-extensions-channel-feishu:2.0.3` 适配器（长连接支持？配置形状？3 秒事件时限如何处理？）；通过则用 channel 路由接入 HarnessAgent，不通过则 oapi-sdk `ws.Client` 手工桥接（兜底路径，可行性报告 §四 4）。
- **FR-C2 对话入口**：事件长连接订阅 `im.message.receive_v1`（单聊权限），仅响应 owner open_id 白名单内的消息，其余静默。
- **FR-C3 异步与幂等**：收到事件即 ack、会话处理异步化（3 秒时限 vs LLM 长响应），按 `message_id` 幂等去重应对重推。

## 四、非功能需求

| # | 需求 | 说明 |
|---|---|---|
| NFR-1 | **opt-in 零回归** | 未配置 `FEISHU_BOT_WEBHOOK`（且未配置通用 webhook）时行为与现状完全一致；collector 现行测试全绿 |
| NFR-2 | **尽力而为语义不变** | 告警发送失败绝不影响任务执行语义（继承 P0-2：3 次退避重试、失败仅 warning 日志） |
| NFR-3 | 限流余量 | 群机器人 100 条/分钟（告警峰值日均个位数，余量两个数量级），不做客户端限流 |
| NFR-4 | 密钥管理 | webhook secret/app secret 走 env 明文（现状惯例），`.env.example`/`README` 环境变量表/`docker-compose.yml` 三处同步（顺带补 `COLLECTOR_ALERT_WEBHOOK` 存量缺口）；~~P1-10 加密设施落地后统一收纳~~ **已关单（2026-10-03）**：P1-10 以独立小特性交付（features/mcp-token-encryption/），拍板裁定 env 类密钥维持 env 口径（同机同文件加密无增益，加密设施仅收库内 MCP token） |
| NFR-5 | 消息体上限 | 按官方 20KB 保守线设计截断策略（FR-A4） |
| NFR-6 | 测试口径 | 单测不真连飞书（mock `urllib.request.urlopen`，与 `tests/test_alerts.py` 同范式）；collector 覆盖率 ≥80% 现行门槛；ruff check/format + lint-imports 通过 |
| NFR-7 | 部署适配 | 通道一仅需出站 HTTPS；通道二长连接仅需出站 WebSocket——裸机 systemd 与 Docker Compose 双轨均免公网入站 |

## 五、验收标准

| 期 | 验收 |
|---|---|
| P0 | ① 配置真实 webhook 后，人为制造任务失败（如断 tushare token 跑单任务），飞书群收到红色卡片，含任务名/错误摘要；② 交易日巡检有滞留时收到橙色卡片；③ 不配置任何新 env 时 `make` 级测试全绿（零回归）；④ `.env.example`/README/docker-compose 三处变量同步 |
| P1 | ① 构造超限持仓（如单票仓位>20%），交易日日终收到预警卡片（含规则名/当前值/阈值）；② 规则 enabled=false 时不推；③ 预警巡检不依赖前端触发 |
| P2 | ① 飞书单聊发「我的持仓怎么样」→ 收到 AI 回复（复用现有 HarnessAgent 工具链）；② 非 owner open_id 发消息无响应；③ spike 结论（channel-feishu 采用/否）记录入设计规格 |

**挂接**：P1 交付时更新 MS-15 交付范围与验收措辞（预警载体=飞书）、新增 ADR 0013（清单见可行性报告 §九）。

## 六、明确不做（YAGNI）

- 账户类通知（邮箱验证/找回密码）走飞书——M01-F06 仍属 SMTP 决策，与本特性互不阻塞
- 多用户绑定：飞书 open_id↔系统用户绑定表、绑定流程、按用户路由（**2026-10-03 变更**：M15 智能情报决策 #18 推翻本条——个性化推送需按用户寻址，绑定表/绑定码/单发路由已随 V3 落地，见 [ADR-0013 变更段](../../../docs/technology/decisions/0013-feishu-messaging.md)）
- 钉钉/企微适配层（`WebhookAlerter` 通用性保留，但只写飞书格式）
- P0 不做 @指定人（需 open_id 查询能力，自建应用就绪后作为 P1 可选增强）
- 消息撤回、图片/文件/语音消息、markdown 消息类型（飞书不支持）
- 前端页内通知体系改动（导航红点/横幅维持现状）
- 客户端限流/告警聚合去重（量级不需要）

## 七、依赖与风险

**依赖（均就绪）**：飞书组织+管理员权限 ✅｜AgentScope 2.0.3（channel-feishu 构件已在线实证存在）✅｜PrincipleRule 契约（`domain/wiki/PrincipleRule.java`，V16）✅｜collector 告警链路（P0-2）✅

**风险**（完整 10 项清单与对策见可行性报告 §八，此处列影响 P0 的）：

| 风险 | 对策 |
|---|---|
| 部署环境对 `open.feishu.cn` 出站连通性（历史 WAF 先例） | P0 动手前在部署机 curl 探测 |
| webhook 请求体上限官方两说（20/30KB） | 按 20KB 保守线设计截断 |
| 免费版权限配额无官方对照表 | 影响通道二（P1 实测），不影响 P0 群机器人 |

## 附：术语

- **群自定义机器人**：飞书群内添加的 webhook 机器人，只能发不能收；`https://open.feishu.cn/open-apis/bot/v2/hook/{token}`
- **自建应用**：企业自有应用，app_id/app_secret 换 tenant_access_token 调 API，可收发消息
- **长连接**：飞书 SDK 内置 WebSocket 事件订阅模式，仅需出站、免公网入站（仅自建应用支持）
- **lark_md**：飞书卡片内的类 markdown 文本标记
- **open_id**：用户/群在应用维度的标识（ou_ 前缀）
