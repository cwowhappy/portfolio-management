# MCP 工具权限审批（HITL）· 设计规格说明

> 对应需求：`../01-requirement/需求规格说明.md`（决策已确认 2026-09-08；同日 grilling 评审定稿）。
> 前置事实：AgentScope 2.0.3 权限确认 interrupt 契约已在本项目集成测试验证（`backend/src/integrationTest/java/com/portfolio/invest/agui/AguiInterruptIntegrationTest.java` 四场景全绿，PR #22）；`@ag-ui/client 0.0.59` 的 `pendingInterrupts`/`runAgent({resume})` 行为与反代 resume 透传已钉住测试（`frontend/tests/agui-stream.test.ts`、`frontend/tests/lib/copilotkit-route.test.ts`）。
> 评审核对补充（2026-09-08）：`useInterrupt` API 按 `@copilotkit/react-core 1.70.1` 实装核对（render 一次性收到含 `interrupts[]` 的 props 对象）；上游 interrupt metadata 键与契约错误文案经 agentscope 2.0.3 字节码核对；MCP 官方 Java SDK（`io.modelcontextprotocol.sdk:mcp-core` 0.17.x，agentscope 传递引入）确认含 streamable HTTP server 传输。

## 一、总体链路

```
Agent 决定调用写性质 MCP 工具（readOnlyHint 缺省/false）
  → McpTool#checkPermissions 返回 ASK（agentscope 内建，无需本项目代码）
  → RequireUserConfirmEvent → 2.0.3 映射为 RUN_FINISHED.outcome.interrupts[]
      （reason:"tool_call"、metadata.agentscope.interruptKind:"permission_confirm"、
        toolName/toolInput/toolContent/replyId、id=replyId:toolCallId）
  → SSE → Next.js 反代（透传，已钉测试）→ CopilotRuntime → @ag-ui/client
  → useInterrupt 检测（runAgent 正常结束 + pendingInterrupts 填充）
  → InterruptApprovalCard 渲染（renderInChat:false，消息流尾部）
  → 用户点「批准/拒绝」→ resolve({approved:true/false})
  → useInterrupt 汇齐全部 open interrupts 后 runAgent({resume:[...]})
  → 反代 trimToLatestUserMessage 对 resume 轮透传（messages:[]）
  → AguiResumeCoordinator 校验 + AguiMessageConverter#toConfirmResultMsg 转 ConfirmResult
  → approved=true：工具执行（state 落 tool_result success）→ Agent 续跑
  → approved=false：工具收到 DENIED 结果 → Agent 续跑
  → 最终文本流回前端（注意：续跑轮不重放 TOOL_CALL_RESULT 事件，见 §五）
```

## 二、后端设计

### UserToolkitFactory（生产代码改动 1/2）

`readOnlyMcpTool(t, client)` → 改名 `mcpTool(t, client)`，readOnly 判定与上游 `McpClientManager`（agentscope 2.0.3）逐字一致：

```java
boolean readOnly =
        t.annotations() != null && Boolean.TRUE.equals(t.annotations().readOnlyHint());
```

其余构造参数不变（name/description/params/outputSchema/client/presetArgs/mcpName）。注释更新：删除「本系统只接只读数据源」的绕过理由，写明规范语义与 FR-1 引用。

### HarnessAgentFactory 系统提示（生产代码改动 2/2，FR-7，决策 4）

系统提示加一句：「工具调用被用户拒绝后，不要原样重试同一调用，改走替代方案或说明无法完成。」防止「拒绝 → LLM 重试 → 反复弹卡」拉锯。不做机械防护（无 N 次熔断类逻辑）。

**interrupt 链路无需其它后端代码**的理由：

- ASK 门来自 `McpTool#checkPermissions`（readOnly → ALLOW；否则 ASK），agentscope 内建（2.0.3 字节码核实）；
- interrupt 映射（`PermissionConfirmEventConverter`）、resume 协调（`AguiResumeCoordinator`）、ConfirmResult 转换全部在 2.0.3 内建；
- 权限上下文保持 trivial（DEFAULT 模式无规则）→ 走轻量路径，工具自身 ASK 门生效（2.0.3 实测确认，调研 §4.4 备注 1）。

### 单元测试（UserToolkitFactoryTest）

TDD：先按三态改断言跑红，再实现。三态：

| readOnlyHint | 期望 `toolkit.getTool(name).isReadOnly()` |
|---|---|
| `true`（`ToolAnnotations(readOnlyHint=true)`） | `true`（不触发审批） |
| 缺省（`annotations() == null`） | `false`（触发审批） |
| `false` | `false`（触发审批） |

既有用例「强制 readOnly=true」断言反转；`disabledTools` 过滤等其余用例不动。

### 集成测试

现有 `AguiInterruptIntegrationTest` 四场景（ASK→interrupt、approved 续跑、denied 续跑、契约错误）保持不动——其 `WriteGateTool` 复刻 `McpTool` 的 ASK 语义（`PermissionDecision.ask`），覆盖审批契约路径。但它的工具**不是真 MCP 工具**，改完后没有任何测试用「真实的、未标 `readOnlyHint` 的 MCP 工具」走通全链路（评审认定的验收缺口）。故**新增 `McpHitlIntegrationTest`（真实 MCP 全链路，本特性验收项）**：

- **测试 MCP server 由后端自供**（评审决策，替代外部 Python server）：classpath 已有 MCP 官方 Java SDK（agentscope 传递引入 `io.modelcontextprotocol.sdk:mcp-core` 0.17.x + `mcp-json-jackson2`），零新增 Gradle 依赖。`integrationTest` 内起一个内嵌 Tomcat（随机端口）挂载 SDK 的 `HttpServletStreamableServerTransportProvider`（原生 Servlet，与 `McpClientPool` 的 `streamableHttpTransport` 客户端形态对齐），`McpServer.sync()` 注册两个工具：
  - `write_note(content)`：**不设 annotations**（→ 客户端侧 `annotations()==null` → 按写处理，触发审批），副作用 = 写临时文件（可断言）
  - `read_note()`：`readOnlyHint=true`（→ 放行不弹卡）
- seed `McpProvider`（AuthType NONE）+ `McpEndpoint` 指向内嵌端口；`/agui/run` 断言沿用 MockMvc——注意 MockMvc 无真实 HTTP 栈，自环 MCP 调用（agent 线程 → HTTP → 本测试 JVM）必须走真 socket，故 MCP servlet 单独起内嵌 Tomcat 而非复用 MockMvc
- 断言：写工具弹卡（interrupt 契约字段）→ 批准 → 临时文件落盘 + Agent 续跑出文本；拒绝 → 无文件 + 续跑；`read_note` 不弹卡直接执行

## 三、前端设计

### 新组件 `frontend/components/chat/InterruptApprovalCard.tsx`

纯展示 + 回调（无 hook，便于单测）：

```tsx
interface Props {
  toolName: string;
  toolInput?: unknown;        // interrupt.metadata.toolInput
  message?: string;           // 兜底说明文案
  onApprove(): void;
  onDeny(): void;
}
```

- 布局复用 `ToolCallCard` 的卡片样式模式（border + 变量色 + 12px 辅助文字）：标题行「需要确认：{toolName}」，入参 JSON 折叠展示（`<details>`），底部「批准 / 拒绝」按钮
- metadata 缺失时以 `message` 兜底（非 agentscope 中断的容错）

### ThreadArea 集成

`useInterrupt` 真实 API（`@copilotkit/react-core 1.70.1` 实装核对）：render **一次性**收到 `{ event, interrupt, interrupts, result, resolve, cancel }`（`interrupt = interrupts[0]`，可为 null；`interrupts` 为全部 open interrupts）；`resolve(payload?, interruptId?)` 不传 `interruptId` 时默认作用于第一个（有 console.warn，不依赖该隐式行为）；全部处理完后由库自动 `runAgent({resume})`。多中断**全部铺开**（决策对 FR-5 的细化）：

```tsx
const interruptBar = useInterrupt({
  renderInChat: false,
  render: ({ interrupts, resolve }) => (
    <>
      {interrupts.map((it) => (
        <InterruptApprovalCard
          key={it.id}
          toolName={it.metadata?.["toolName"] ?? "未知工具"}
          toolInput={it.metadata?.["toolInput"]}
          message={it.message}
          onApprove={() => resolve({ approved: true }, it.id)}
          onDeny={() => resolve({ approved: false }, it.id)}
        />
      ))}
    </>
  ),
});
```

- 渲染位置：`{interruptBar}` 放消息列表尾部——现有 24px 占位（`ThreadArea.tsx:527` 的 `<div className="h-6" />`）改为挂载点，位于 sendError 横幅与 Composer 之上。注意：`renderInChat:false` 时 hook 返回 React 元素，**必须手动渲染返回值**；ThreadArea 当前没有任何「流式状态指示」组件可复用（评审核对：全前端不存在该组件）
- 不使用 `cancel()`：拒绝即 `approved:false`（Agent 收到 denied 后继续），语义完整
- 续跑链路复用现有机制：汇齐逻辑在 react-core 内（自动 `runAgent({resume})`），持久化监听（`agent.messages` 变化防抖）、错误横幅（RUN_ERROR）、isRunning 状态均不变

### 契约错误人话化（FR-8，决策 5）

`ThreadArea.tsx:392` 的 catch 是唯一错误文案出口（`e.message` 逐字上横幅，"HTTP 502" 测试钉住）。加一个映射 helper：识别上游两条稳定文案（2.0.3 字节码核对）——

- `Thread has unresolved interrupts; RunAgentInput.resume must address all of them`（刷新丢卡后同线程发普通消息）
- `RunAgentInput.resume does not match any open interrupt`（服务端丢中断后点批准）

→ 显示：「当前对话有未完成的审批（可能因页面刷新或服务重启失效），请开启新对话继续。」其余错误原文案不受影响。若实测 `e.message` 携带 code（`AGUI_INTERRUPT_CONTRACT_ERROR`），优先按 code 匹配，文案子串作 fallback。

### 前端测试

1. `InterruptApprovalCard.test.tsx`（新）：渲染 toolName/toolInput/message 兜底；按钮回调触发
2. `ThreadArea.test.tsx` **与 `ThreadArea.stream.test.tsx`（两文件都要）**：mock `@copilotkit/react-core/v2` 为整体替换工厂，`ThreadArea` 一旦 import `useInterrupt`，两处必须同步加键（如 `useInterrupt: (config) => { mocks.interruptConfig = config; return mocks.interruptElement ?? null; }`），否则 `useInterrupt is not a function` 直接崩。增补断言：① render 收到 `interrupts` 数组并逐张渲染卡片；② 卡片按钮调用 `resolve({approved:true/false}, interruptId)`（经 render props 传导断言参数含 interruptId）；③ 线程切换行为钉住（useInterrupt 的 interrupt 状态归 agent/thread，切线程卡片消失或保留以实测为准）
3. 契约错误翻译测试（新或并入 ThreadArea.test.tsx）：runAgent reject 且 message 为上游两条文案之一 → 横幅显示中文引导文案；其余错误（如 "HTTP 502"）文案不受影响

## 四、错误处理

| 场景 | 行为 |
|---|---|
| 契约错误（`AGUI_INTERRUPT_CONTRACT_ERROR`） | 正常路径不发生（`useInterrupt` 汇齐全部 open interrupts 才提交）。触发场景：刷新丢卡后同线程发普通消息 / 服务端丢中断后点批准 → `ThreadArea` 错误处理按 FR-8 映射为中文提示并引导开新对话（上游两条文案为稳定字面量，已字节码核对） |
| 续跑轮 RUN_ERROR（上游故障） | 现有错误横幅 + 部分消息保留（ThreadArea.stream.test.tsx 已覆盖该模式） |
| 审批后 Agent 长时间无响应 | 现有 stop 按钮（abortRun）可用；中断状态留在服务端，见已知限制 |
| 拒绝后 Agent 重试同一工具 | 接受（不做机械防护）；FR-7 提示词约束收敛重试倾向，上线后观察 |

## 五、已知限制（接受并记录，不做于本次）

1. **续跑轮不重放工具事件**：2.0.3 实测，`TOOL_CALL_RESULT` 在续跑流中被 `hasStartedToolCall` 抑制——审批卡片不能依赖 result 事件判断「已执行」，工具执行依据是续跑完成 + 最终文本（后端 state 落 `tool_result success`）。前端持久化（ADR-0004 精简历史）本就不存工具调用，无影响。
2. **页面刷新丢失审批卡片**：`pendingInterrupts` 是客户端内存态，刷新后卡片消失；后端 `AguiResumeCoordinator` 仍持有 pending interrupt（服务端内存态），用户在同线程再发普通消息将收到契约错误——文案已按 FR-8 翻译为中文并引导新线程，恢复机制列入后续治理。
3. **服务端重启丢失 pending interrupt**：与 2 相反方向的丢失——后端重启后 `AguiResumeCoordinator` 的服务端内存态清空，前端卡片仍在，点「批准」收到「resume 不匹配」契约错误 → FR-8 中文兜底。恢复机制与 2 一并列入后续治理。
4. **审批卡片无 MCP server 来源**：上游 interrupt metadata 仅含 `toolName/toolInput/toolContent/replyId`（字节码核对），无 `mcpName` 且映射在 2.0.3 内建、本项目无注入点。随 provider 信任配置治理时一并解决。
5. **打扰面**：未标 `readOnlyHint` 的 MCP 数据源工具全部弹审批（决策 1 的知情选择）。缓解路径（后续立项）：规则沉淀 / provider 信任配置。
