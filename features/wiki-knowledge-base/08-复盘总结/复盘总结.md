## 二、经验（做对了什么）

1. **计划代码样例对照真实代码核实的红利**（memory 既定偏好）：20 任务的简报代码 verbatim 落地率极高，仅 2 处编译级笔误（对比 MS-09 样例先验三处全错）——计划期 Read 真实签名/模式的一次性投入，换来执行期零返工。
2. **逐任务「简报 + 独立审查」门禁拦截力**：两处 Important 缺陷（新建保存后表单不清空可致重复创建、交付文档测试计数错）均在任务审查轮被拦、修复轮一次收敛；审查者的 git 实证（`git log` 数测试方法 560+38=598）纠正了控制器补充清单给的错数——**引用计数必须 git 实证**在本里程碑内被双向验证。
3. **Testcontainers 集成测试直接验证迁移链**：`@DataJpaTest` + FlywayAutoConfiguration 以真实 V1→V16 全链启动，schema 正确性、UNIQUE 约束、用户隔离（`findByIdAndUserId` 双重保障）全部 DB 级钉住，不依赖「单测绿≈schema 对」的推断。
4. **e2e 以 DB 落库为验收证据**：除页面断言外直接查库取证（seeding 条数、industry_code 落库），证明力高于「页面绿了」；空库门控「空数组才 skip」范式复用零成本。
5. **台账作为中断恢复地图**：会话中断后实现者经 SendMessage 从断点续跑（磁盘工作区状态与 git 对账先行），零重复劳动——SDD 台账 + git log 的可靠性在本里程碑实测。

## 三、不足

1. **同类计划盲区跨里程碑重犯**：①既有迁移版本断言测试未排新版本号（MS-09 偏差 #5 同型，本里程碑再踩）；②新 FK 表未同步 `scripts/e2e-cleanup.sh`（三份计划均未列，终审才兜住，期间 dev 库已累积 56 个 e2e 残留用户）——两类的根因都是「新增迁移的配套动作」无 checklist。
2. **控制器（编排者）给交付文档的补充清单带错数**：「前端新增 25」实为 38——审查链兜住，但编排者引用汇总数字未 git 实证，与要求实现者的标准不一致。
3. **交互坚固性 deferred 三处同族**：保存按钮无 in-flight 防连点（NoteEditor/RulePanel/ResearchNoteDialog）+ 删除/启停失败静默吞错——沿袭 journal `EntryEditor` 既有惯例，技术债整体沿袭而非新增，但同族分散。
4. **IDE 诊断误报消耗判断成本**：新建文件频繁报「Cannot find module / cannot be resolved」（TS server 索引滞后），每个任务都需以 gradle XML/tsc 证据裁决一次——无自动降噪手段，靠派发指令预标注。

## 四、优化建议

1. **「新增 Flyway 迁移」checklist 固化**（本里程碑与 MS-09 各踩其一，制度化一次拦全）：①版本断言测试补版本号；②`scripts/e2e-cleanup.sh` 按依赖序补 FK 表 DELETE（本次顺手可补既有遗漏的 `skill_user_config`/`watchlist_item` 两表）；③DDD 分包规范域清单登记。建议写入 `docs/technology/conventions/` 或计划模板。
2. **编排者/计划的引用计数一律 git 实证**（`git diff` 数测试方法、`git log -S` 归因），不凭汇总记忆——本里程碑双向验证其必要性。
3. **保存类交互统一加固**：in-flight 禁用 + 失败行内提示抽公共处理（三处新组件 + journal 既有 `EntryEditor` 一次收口），建议列入 MS-12 前的体验加固小任务。
4. **DDD 规范文档补登 analytics 域与 Analytics/Watchlist 控制器**（MS-07/MS-10 遗留债，本次终审确认实有 13 包而文档列 12）——纯文档对齐，半小时内可清。
