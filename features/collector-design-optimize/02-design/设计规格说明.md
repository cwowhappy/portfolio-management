## 一、总体架构

保持「采集(写)与查询(读)分离」「业务表 schema 由 Java 后端 Flyway 单一拥有」原则，将单一脚本重构为可扩展采集框架。

```
collector/（Python 3.12，独立服务）
  config.py              环境变量 + YAML 配置加载
  cli.py                 手动执行入口（python -m collector.cli run/list/backfill）
  model/                 规范记录（canonical record）与数据类型定义
  sources/               数据源适配器 Source（可配置通用源 + 自定义源）
  converters/            格式转换器 Converter（声明式字段映射 + 自定义）
  calc/                  计算步骤（聚合，可选）
  validators/            校验器 Validator（声明式规则 + 自定义）
  tasks/                 采集任务 Collector（绑定源/转换/校验/目标表/调度）
  executor/              执行器 Executor + 选源器 SourceSelector
  scheduler/             APScheduler 装配 + 交易日历门控 + 并发互斥
  store/                 psycopg 幂等 upsert（通用 writer + 每表 SQL）
  migrations/            collector 自有运维表迁移（任务/执行历史/源健康）
        │ 写业务数据（零 DDL，对齐 Java Flyway 表）
        ▼
PostgreSQL
  业务表（Java Flyway 拥有）：V3 现有 5 表 + V4 新增 treasury_yield_curve / index_constituent
  运维表（collector 自有）：collector_task / collector_task_run / collector_source_health
```

**依赖方向**（单向）：`tasks → {sources, converters, calc, validators, store}`；`executor → {sources, converters, calc, validators, store, tasks}`；`scheduler → {executor, tasks}`；`cli → {executor, tasks}`。`sources/converters/validators` 不 import `executor/store/scheduler`，保持与现有「adapter 不碰 DB/编排」一致。

## 二、核心抽象

### 2.1 Source（数据源适配器）

```python
class Source(ABC):
    source_id: str
    supports_range: bool = False   # 是否支持按区间回填

    @abstractmethod
    def fetch(self, params: dict) -> pd.DataFrame:
        """返回原始数据（DataFrame）。params 含 start/end 等运行时参数。"""
```

- `ConfigurableSource`：读 YAML 声明（`type: akshare|tushare|http` + `call` + 固定参数），内部通过反射/注册表调用对应库函数，**零代码扩展**。
- 自定义 `Source` 子类：复杂逻辑（如申万映射需 31 次 `index_member_all` 循环）。

### 2.2 Converter（格式转换器）

```python
class Converter(ABC):
    @abstractmethod
    def convert(self, raw: pd.DataFrame) -> list[dict]:
        """原始数据 → 规范记录（list[dict]，键对齐目标表列，类型确定）。"""
```

- `FieldMappingConverter`：读 YAML 列映射（`{from, type, unit, default, clean}`），覆盖绝大多数「接口调用 + 列名/类型归一」场景。
- 自定义 `Converter` 子类：跨列派生、条件逻辑等。

### 2.3 Calc（计算，可选）

```python
class Calc(ABC):
    @abstractmethod
    def compute(self, records: list[dict]) -> list[dict]:
        """规范记录 → 聚合后的规范记录（如全A中位数、行业市值加权）。"""
```

- 仅在计算型任务挂载（全A估值快照、行业加权估值）；采集型任务跳过（恒等）。

### 2.4 Validator（校验器）

```python
class Validator(ABC):
    @abstractmethod
    def validate(self, records: list[dict]) -> tuple[list[dict], list[ValidationIssue]]:
        """返回（通过/清洗后的记录, 校验问题列表）。"""
```

- `RuleValidator`：读 YAML 规则（`required/not_null/type/range/unique/min_rows/allowed_values`），按 `hard`/`soft` 分级处理。
- 自定义 `Validator` 子类：跨字段/跨表校验。

### 2.5 SourceSelector（选源器）与可靠性评分

```python
class SourceSelector:
    def select(self, sources: list[Source], health: dict[str, SourceHealth]) -> list[Source]:
        """过滤熔断中的源，其余按评分降序返回（评分相同按声明优先级）。"""
```

**健康度模型（每源一个「评分 + 熔断器」）**，状态由字段派生，不存状态列：

- 熔断三态（阈值 N=3、冷却 C=10min，参数可调）：
  - `closed`（可用）：`consecutive_failures < N`
  - `open`（跳过）：`consecutive_failures ≥ N` 且 `now - last_failure_at < C`
  - `half-open`（试探一次）：`consecutive_failures ≥ N` 且冷却期已过
- 评分公式（确定性，写入 `source_health.score`）：
  `score = 100 × success_rate − latency_penalty − consecutive_failure_penalty`
  其中 `success_rate = success_runs / total_runs`（冷启动 `total_runs=0` → 取中性 50 分），`latency_penalty = min(30, last_latency_ms/1000 × 5)`，`consecutive_failure_penalty = min(40, consecutive_failures × 20)`。

**选源算法**：

```python
def select(sources, health):
    candidates = []
    for priority, src in enumerate(sources):     # 按声明优先级
        h = health.get(src.source_id)
        if state(h) == 'open':                   # 熔断中 → 跳过
            continue
        candidates.append((score(h), priority, src))
    candidates.sort(key=lambda x: (-x[0], x[1]))  # 评分降序，同分按声明优先级
    return [src for _, _, src in candidates]
```

**健康度更新**（执行后写回 `collector_source_health`）：

```python
def record_success(src, rows, latency):
    total_runs++, success_runs++, consecutive_failures = 0
    last_latency_ms = latency, last_success_at = now, recompute_score()

def record_failure(src, err):
    total_runs++, consecutive_failures++
    last_failure_at = now, last_error = err, recompute_score()
```

成功清零 `consecutive_failures` → half-open 试探成功即恢复 `closed`；试探失败则刷新 `last_failure_at` → 重新 `open` + 重新冷却。

### 2.6 Collector（采集任务）

```python
class Collector:
    task_code: str
    sources: list[Source]        # 有序（声明优先级）
    converter: Converter
    calc: Calc | None
    validator: Validator
    target_table: str
    schedule: ScheduleSpec
```

任务由 DB `collector_task` 表描述；`Collector` 是执行器的输入视图，由 `TaskRepository` 从 DB 装配。

### 2.7 Executor（执行器）

```python
class Executor:
    def run(self, task: Collector, mode: str, params: dict) -> RunResult:
        """选源 → 拉取 → 转换 → 计算 → 校验 → 落库 → 记历史/更新健康。"""
```

### 2.8 Store（存储层）

- 通用 `upsert(conn, table, records)` 走 `executemany` + 单事务；每表提供列对齐的 upsert SQL（`ON CONFLICT DO UPDATE`），零 DDL。

### 2.9 Registry（注册表）与装配

- 声明式扩展经 **Registry** 把配置解析为对象：`SourceRegistry` / `ConverterRegistry` / `CalcRegistry` / `ValidatorRegistry`，各维护 `type → 工厂` 映射。
- 示例：`{type: akshare, call: stock_zh_a_spot_em}` → `ConfigurableAkshareSource`；`{type: plugin, class: shenwan_mapping}` → 按名加载自定义 `Source` 子类。
- 任务装配：`collector_task` 的 JSONB（`source_ids`/`validator`）与名称列（`converter`/`calc`）经 Registry 组装成 `Collector` 对象，供 Executor 消费。

## 三、数据模型

### 3.1 表分类与关系

```
业务表（Java Flyway 拥有，collector 只 INSERT/UPDATE）
```

### 3.2 业务表（Java 拥有）

**V3 现有 5 表**（collector 迁移目标，列/约束见 `V3__valuation.sql`）：

| 表 | 用途 | 关键约束 |
|---|---|---|
| valuation_snapshot | 全A估值快照（中位数/破净） | UNIQUE(trading_day) |
| treasury_yield | 10Y 国债（**废弃中**） | UNIQUE(trading_day) |
| index_valuation_history | 指数 PE/PB/股息率 | UNIQUE(trading_day, index_code) |
| industry_valuation | 行业加权估值 | UNIQUE(trading_day, industry_code) |
| shenwan_industry_mapping | 申万映射 | UNIQUE(stock_code) |

**V4 新增 2 表**：

```sql
-- 多期限国债收益率曲线（长表，term 区分期限）
CREATE TABLE treasury_yield_curve (
    id BIGSERIAL PRIMARY KEY,
    trading_day DATE NOT NULL,
    term VARCHAR(16) NOT NULL,          -- '1Y','3Y','5Y','10Y','30Y'
    yield NUMERIC(8,4) NOT NULL,
    UNIQUE (trading_day, term)
);

-- 指数成分股
CREATE TABLE index_constituent (
    id BIGSERIAL PRIMARY KEY,
    index_code VARCHAR(16) NOT NULL,
    stock_code VARCHAR(16) NOT NULL,

```

**10Y 归属（已决策：废弃 `treasury_yield`）**：ERP 读侧切换到 `treasury_yield_curve`（term='10Y'），旧表 `treasury_yield` 废弃。V4 迁移顺序：① 建 `treasury_yield_curve`；② 将 `treasury_yield` 现有 10Y 历史行迁移到曲线表（`INSERT ... SELECT trading_day, '10Y', yield_10y`）；③ 待 Java 读侧切换到曲线表后 `DROP TABLE treasury_yield`（可放 V5 或同版本后置步骤，避免读侧短暂断数据）。collector 仅写曲线表（含 10Y），不双写。此为**跨服务变更**，需 Java 读侧同步切换，部署顺序：先建表+迁数据 → 读侧切换 → 删旧表。

**指数股息率不新增表**：`index_valuation_history.dividend_yield` 列已存在（现恒为 None），接入股息率源后填入即可。

### 3.3 运维表（collector 拥有，alembic raw SQL 迁移）

```sql
CREATE TABLE collector_task (
    id BIGSERIAL PRIMARY KEY,
    task_code VARCHAR(64) NOT NULL UNIQUE,     -- 任务唯一标识（= 数据类型，1:1）
    task_name VARCHAR(128) NOT NULL,
    source_ids JSONB NOT NULL,                  -- 有序源列表（见 §3.4）
    converter VARCHAR(64) NOT NULL,             -- 转换器名（Registry 解析）
    calc VARCHAR(64),                           -- 计算步骤名，可空（采集型任务无）
    validator JSONB,                            -- 校验规则（见 §3.4）
    target_table VARCHAR(64) NOT NULL,
    schedule JSONB NOT NULL,                    -- 调度（见 §3.4）
    enabled BOOLEAN NOT NULL DEFAULT true,
    trading_day_gated BOOLEAN NOT NULL DEFAULT true,
    retry_max INT NOT NULL DEFAULT 3,
    retry_backoff VARCHAR(16) NOT NULL DEFAULT 'exponential',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_collector_task_enabled ON collector_task (enabled);

CREATE TABLE collector_task_run (
    id BIGSERIAL PRIMARY KEY,
    task_id BIGINT NOT NULL REFERENCES collector_task(id),
    mode VARCHAR(16) NOT NULL DEFAULT 'incremental',  -- incremental | backfill
    status VARCHAR(16) NOT NULL,          -- running | success | partial | failed | skipped
    source_used VARCHAR(64),
    params JSONB,                         -- 运行时参数（回填区间/date）
    rows_written INT,
    started_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at TIMESTAMPTZ,
    error TEXT,
    message TEXT                          -- 降级/soft 校验等说明
);
CREATE INDEX idx_collector_task_run_task ON collector_task_run (task_id, started_at DESC);
CREATE INDEX idx_collector_task_run_status ON collector_task_run (status);

CREATE TABLE collector_source_health (
    id BIGSERIAL PRIMARY KEY,
    source_id VARCHAR(64) NOT NULL UNIQUE,
    total_runs INT NOT NULL DEFAULT 0,
    success_runs INT NOT NULL DEFAULT 0,
    consecutive_failures INT NOT NULL DEFAULT 0,
    last_latency_ms INT,
    last_success_at TIMESTAMPTZ,
    last_failure_at TIMESTAMPTZ,
    last_error TEXT,
    score NUMERIC(5,2),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE trading_calendar (
    trade_date DATE PRIMARY KEY
);
```

迁移工具：**alembic（raw SQL 模式，不引 ORM）**，对齐 Java 后端 Flyway 心智——版本化、可回滚、可追踪。初始 revision 建 4 张运维表；后续 schema 演进新增 revision。启动/部署时执行 `alembic upgrade head`。数据访问统一 psycopg raw SQL（业务表 upsert + 运维表 repository CRUD），不引入 SQLAlchemy ORM。

## 四、装配、调度、并发互斥与手动执行

### 4.0 装配与启动流程（Composition Root）

```
启动 main()：
  1) alembic upgrade head                    # 建/升级运维表
  2) seed_tasks(config)                       # YAML 任务定义 → collector_task 幂等 upsert
  3) 构建无状态全局：selector / executor / calendar
  4) 从 DB 读 enabled 任务 → 经 Registry 装配 Collector 对象
  5) 为每个任务装配 APScheduler job（触发 TaskRunner）
```

- **任务定义源**：YAML 是权威定义（source/converter/validator/target/schedule/enabled），启动时 seed 幂等同步到 `collector_task`（`ON CONFLICT (task_code) DO UPDATE`，**不覆盖 `enabled`**，保留 DB 里的运行时开关）。
- **注册表（Registry）**：`type → 工厂` 解析声明为对象（见 §2.9）；代码插件按名注册。

### 4.1 TaskRunner（统一执行入口）

Scheduler 与 CLI **都调 `TaskRunner`**，保证两条路径行为一致：

```python
class TaskRunner:
    def run(self, task, mode='incremental', params=None, force=False) -> RunResult:
        if task.trading_day_gated and not force and not calendar.is_trading_day(today):
            return skipped('非交易日')
        with psycopg.connect(database_url) as conn:      # 每次运行独立连接
            key = hashtext(task.task_code)
            if not conn.try_advisory_lock(key):           # 互斥
                return skipped('上一实例运行中')
            try:
                return self._run_with_retry(conn, task, mode, params)
            finally:
                conn.unlock_advisory_lock(key)

    def _run_with_retry(self, conn, task, mode, params):
        for attempt in 1..retry_max:
            try:
                return executor.run(task, mode, params, conn)
            except (AllSourcesFailed, StoreError):        # 源全失败 / DB 错误 → 重试
                if attempt < retry_max: sleep(backoff(attempt)); continue
                raise
```

- **连接管理**：advisory lock 为 session 级，**锁与后续工作共用同一连接**；并发任务各自独立连接（APScheduler 线程池）。
- **Executor 无状态**：`Executor(selector)` 单例，`run(..., conn)` 传入连接，store/health/run 复用该连接。
- **重试层级**：源侧降级在 Executor 内（换源）；「源全失败 / DB 错误」上抛给 TaskRunner 做整任务重试。

### 4.2 调度

- 每个 `enabled` 任务装配一个 APScheduler job（`CronTrigger`/`IntervalTrigger` 由 `schedule` 字段决定），`coalesce=True + max_instances=1`，job 函数 = `TaskRunner.run`。
- 任务启停/改调度：改 DB 后重启生效（一期不做热重载）。

### 4.3 交易日历门控

- 交易日历：优先 akshare 交易日历接口，落地到运维表 `trading_calendar`（启动时拉取 + 定期刷新）；非交易日跳过（在 `TaskRunner.run` 内判断）。
- 手动 `--force` 跳过门控（补数/回填不受日历约束）。

### 4.4 同任务并发互斥

- `pg_try_advisory_lock(hashtext(task_code))`：拿不到 → `task_run(status=skipped)`；拿到 → 执行，`finally` 释放（见 §4.1）。
- DB 锁同时覆盖「调度重叠」与「手动 vs 调度」两类冲突，多实例安全。

### 4.5 CLI 命令与参数

`python -m collector.cli <command> [options]`（CLI 是 `TaskRunner` 的薄封装，与调度同一入口）：

| 命令 | 参数 | 说明 |
|---|---|---|
| `run <task_code>` | `--force`；`--date YYYY-MM-DD`（默认今天） | 手动触发一次增量采集；`--date` 指定交易日（补某天快照） |
| `list` | `--enabled-only` / `-e` | 列任务（schedule / enabled / 上次运行状态） |
| `backfill <task_code>` | `--start YYYY-MM-DD`（必填）；`--end YYYY-MM-DD`（必填）；`--force` | 按区间回填历史 |
| `seed` | `--dry-run` | YAML → DB 幂等同步（`--dry-run` 只打印差异） |
| `history <task_code>` | `--limit N`（默认 20） | 查执行历史 |

## 五、数据流与错误处理

### 5.1 单次执行管道

```
Executor.run(task, mode, params)
  1) 选源      SourceSelector.select(sources, health) → 有序可用源
  2) 拉取      source.fetch(params)                     → raw DataFrame
  3) 转换      converter.convert(raw)                   → records
  4) 计算      calc.compute(records)  (可选)            → records
  5) 校验      validator.validate(records)              → records + issues
  6) 落库      store.upsert(conn, table, records)       → rows_written
  7) 记录      task_run 落库；source_health 更新（成功率/延迟/失败）
```

### 5.2 降级与重试

**降级循环（关键：区分「源侧」与「目标侧」错误）**：

```python
def run(task):
    candidates = selector.select(task.sources, health)
    if not candidates:
        return failed("所有源熔断或不可用")
    for src in candidates:
        try:
            # 源侧：fetch → convert → calc → validate（hard 失败抛异常）
            raw = src.fetch(params)
            records = task.converter.convert(raw)
            if task.calc: records = task.calc.compute(records)
            records, issues = task.validator.validate(records)
            # 目标侧：落库（幂等单事务）——失败不换源，向上抛走整任务重试
            task.store.upsert(records)
            health.record_success(src, len(records), latency)
            return success(source_used=src.source_id, rows=len(records))
        except SourceError as e:       # 仅源侧异常（fetch/convert/validate）
            health.record_failure(src, e)
            logger.warning("源 %s 失败，降级下一源", src.source_id)
            continue
    return failed("全部源失败")
```

- **多源降级**：仅「源侧」错误（fetch/convert/calc/validate）触发换源；`store.upsert` 的 DB 异常不在 `SourceError` 内，直接向上抛——换源不能解决 DB 问题。
- **整任务重试**：`retry_max` 次，指数退避（`retry_backoff=exponential`，如 30s/60s/120s，替换现固定 30s）。
- **失败隔离**：每源在「落库前」失败，已成功落库的数据不回滚；`status=partial` 表示「降级了但仍有数据」。
- **硬/软校验**：hard 失败 → 视为该源失败（抛 `SourceError`），走降级；soft 失败 → 记 `message`，剔除异常行继续落库。

### 5.3 速率控制

- 数据源调用统一经 `RateLimiter` 装饰（简单令牌桶或调用间隔，如 tushare 循环调用间 0.5s），降低上游限流风险；不引入重依赖。
- 循环取数（如申万映射 31 次 `index_member_all`）在 `Source` 内由 `RateLimiter` 约束调用间隔。

## 六、任务间数据依赖与回填机制

### 6.0 任务间数据依赖

- 日频「行业加权估值」任务依赖申万映射：映射由**周频**「申万映射」任务维护于 `shenwan_industry_mapping` 表，行业估值任务**读取该表**（最近一次映射结果），而非每日重拉 tushare（消除「每日 31 连发」浪费）。
- 一期不引入显式任务依赖编排（YAGNI）；依赖关系通过「上游任务先落库、下游任务读库」解耦，读取不到映射时行业估值任务降级为 partial。

### 6.1 回填机制

- `Source.supports_range=true` 的任务可回填。
- CLI：`python -m collector.cli backfill <task> --start 2016-01-01 --end 2026-08-28 [--force]`。
- 回填复用 5.1 管道，`mode=backfill`、`params={start, end}`；幂等 upsert 保证重复执行无脏数据；批量写入走 `executemany` 单事务（修掉「逐行 commit」缺口）。
- 一期迁移现有 `backfill.py`（指数 PE/PB 历史）到通用回填 runner，并扩展支持国债收益率曲线回填。

## 七、配置示例（声明式）

```yaml
# collector/tasks/all_a_valuation.yaml
task: all_a_valuation
data_type: valuation_snapshot
sources:
  - { source_id: akshare_spot_em, priority: 1, type: akshare, call: stock_zh_a_spot_em }
  - { source_id: tushare_daily_basic, priority: 2, type: tushare, call: daily_basic }
converter:
  type: field_mapping
  columns:
    code:       { from: 代码, type: str }
    name:       { from: 名称, type: str }
    pe:         { from: 市盈率-动态, type: numeric }
    pb:         { from: 市净率, type: numeric }
    market_cap: { from: 总市值, type: numeric }
calc: snapshot_median        # 全A中位数/破净（计算型）
validator:
  rules:
    - { field: code, check: required, level: hard }
    - { field: pe, check: range, min: 0, max: 100, level: soft }
    - { check: min_rows, value: 1000, level: hard }
target_table: valuation_snapshot
schedule: { type: cron, cron: "30 15 * * 1-5", trading_day_gated: true }
```

复杂任务（申万映射、行业加权）以 `Source`/`Converter`/`Calc` 子类实现，接口与声明式一致。

## 九、部署与可观测性

- `docker-compose` 的 `collector` 服务不变；新增 `collector.cli` 手动入口（`make collect` 保留，扩展 `make collect-task run <task>` 等）。
- 启动前执行 `alembic upgrade head`（建/升级 collector 运维表，与 Java 启动跑 Flyway 对称）。
- 环境变量：`DATABASE_URL` / `TUSHARE_TOKEN`（既有）+ 新增数据源所需（中证/中债如需）。
- 可观测性：结构化日志 + `collector_task_run`（执行历史）+ `collector_source_health`（源健康），替换当前「仅日志」。
- 交易日历缓存需定期刷新；容器 `TZ=Asia/Shanghai` 补 `tzdata`（既有已知缺口）。

## 十、明确不做（YAGNI）

- 数据导出、HTTP 管理 API / UI、分布式任务队列、workflow 编排。
- 可靠性评分的自适应/机器学习调权。
- 热重载任务调度（改 DB 即时生效）；一期重启生效。
- 二期数据类型的实际接入（可转债/基金/宏观/信用债/个股历史估值等）。
