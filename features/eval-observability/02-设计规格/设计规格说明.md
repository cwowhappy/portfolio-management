## 二、eval 执行链

### 2.1 打包：独立 evalBootJar（BootJar 自定义任务）

生产 jar 保持零污染（不含 eval 类/资源——现状 plain jar 内 `invest/eval` 条目数 0，`backend/build/libs` 实测），新增 Gradle 任务：

```groovy
tasks.register('evalBootJar', org.springframework.boot.gradle.tasks.bundling.BootJar) {
    archiveClassifier = 'eval'
    mainClass = 'com.portfolio.invest.eval.EvalRunner'
    classpath = sourceSets.eval.runtimeClasspath   // 含 main.output + eval resources(rubric/questions)
}
```

依据：`BootJar` 公开 API `classpath(Object...)`（Boot 4.0.3 jar javap 实证）；`sourceSets.eval.runtimeClasspath` 已接线 `+= sourceSets.main.output`（build.gradle:59-65）且 `evalRuntimeOnly.extendsFrom runtimeOnly`（:66-69）——eval 资源（rubric/questions/extraction）与 main 资源（application.yml/skills）随 jar 打包，`java -jar app-eval.jar --key=value` 与 `EvalRunner.java:117-133` 现有命令行参数形态直接对齐（Boot loader args → Spring 属性）。`make build`（Makefile:78-79）追加 evalBootJar；部署方案在 app.jar 旁分发 `app-eval.jar`（发布文档更新项）。`compileEvalJava` 防漂断（build.gradle:238-242）不动。

`make eval-agent`/`eval-extraction` 本地开发入口不变（仍走 JavaExec + `injectDeepseekEnv`）。

### 2.2 调度器与子进程环境

`EvalScheduler`（`@Scheduled(cron = "0 17 2 * * *", zone = "Asia/Shanghai")`——02:17 错峰：02 点档现有任务全空，最近为 04:07 清理（`IntelligenceCleanupService.java:74`）；顶层 try/catch 护调度线程沿 10 任务先例）：

1. **互斥锁**：单实例 `AtomicBoolean running`（手动与定时互斥，进行中再触发返回 409 语义）。
2. **env 白名单**：`ProcessBuilder.environment()` 只放行 `DEEPSEEK_API_KEY/DEEPSEEK_MODEL/DEEPSEEK_BASE_URL`、`SPRING_DATASOURCE_*`（eval schema 指向）、`SPRING_PROFILES_ACTIVE`、`TZ`、`EVAL_*`——**其余全剔除**。效果：`AdminSeedRunner` 读 `ADMIN_USERNAME/PASSWORD` 缺席 → log.warn 跳过（`AdminSeedRunner.java:35-38`）；`DevMarketDataSeedRunner`/`HitlE2eSeedRunner` 同理缺席即 return（各自 :37-39/:37）——**三个 seeder 零代码改动被禁**；飞书/邮件凭证缺席 → 外呼天然不可能。
3. **命令构造**（Task 2 实证修正）：`java -jar <evalJar> --invest.eval.data-root=<dataDir>`——**仅此一参 + env 白名单**（datasource/hikari/allow-bean-definition-overriding/state-root/server.port/REMEMBER_ME_KEY 等覆盖项由 EvalRunner 内部构造，`Options.parse` 拒绝未知命令行参数）。env `SPRING_DATASOURCE_*`（或 `EVAL_DATASOURCE_URL` 显式指定）传入库位置，URL 的双段 currentSchema 由 `EvalPostgresProvisioner` 规范化产出。报告路径 `--eval.report-path`（Task 6 传入）。datasource 缺省回退主 datasource 同 host/db（单机部署同实例）。
4. **超时看护**：`process.waitFor(timeout)`（默认 120 分钟可配）超时 `destroyForcibly` → 收割按 PARTIAL 语义。
5. **退出后**：调 `EvalHarvester.harvest(runId, reportPath, exitCode)`。

## 三、阈值判定与告警

### 3.1 判定算法（`EvalRegressionJudge`，纯函数）

输入：本跑 `RunResult{completeness, totalPass/totalFail/totalError, byCategory: Map<String,CategoryScore>}` + baseline 跑同构数据。输出：`JudgeVerdict{degraded: bool, reasons: List<String>, recovered: bool}`。

- **劣化判定**（任一命中）：
  - 总通过率降幅 ≥ `passRateDropThreshold`（默认 10 个百分点）；
  - PASS→FAIL 翻转数 ≥ `flipThreshold`（默认 3，按同题 id 对齐——题库 hash 不同即视为不可比，跳过翻转判定只判降幅）；
  - 三新类任一分类通过率降幅 ≥ `categoryDropThreshold`（默认 15 个百分点）。
- **无 baseline**（首跑/基准变更后）：不判劣化，输出 `NO_BASELINE`（运行表 alert_status=NONE，理由记录）。
- **不可比**（题库 hash 或 rubric 版本 ≠ baseline 的）：降级只判「绝对完成率」（总 PASS+ERROR 题数 / 应跑题数 < 80% 告警），reasons 标 `BASELINE_INCOMPARABLE`。
- **恢复判定**：上一跑 degraded=true 且本跑无命中 → `recovered=true`，本跑置 baseline_candidate。

### 3.2 告警发送与状态机

复用 `AlertNotifier.send(title, template, bodyLines)`（`application/alert/AlertNotifier.java:8` → 飞书卡片）；邮件降级沿三处先例模式（`PrincipleAlertService.java:137-159` 的 notifier-失败-则-mail 形态复制到 harvester）。

- 劣化卡（红）：标题 `【eval 回归告警】<日期>`；行：总通过率 A→B（降幅）、翻转清单（题 id + 一行 diff）、劣化分类、运行链接（runId）、「基准：题库 hash 短码 / 提示词版本短码」。
- 恢复卡（蓝）：标题 `【eval 回归恢复】`；行：恢复时间、本跑通过率、`baseline_candidate=true 待人工确认`。
- `eval_run.alert_status` ∈ {NONE, DEGRADED, RECOVERED, DEGRADED持续}——留痕以库表为准（NFR-7），飞书是通知通道。

## 五、观测采集

### 5.1 工具调用级（decorator 增量改造）

`RecordingAgentToolDecorator.callAsync`（`RecordingAgentToolDecorator.java:146-164`）最小增量：

```java
long t0 = System.nanoTime();                                    // Mono.defer 前（:157 附近）
return Mono.defer(() -> { ...
    return delegate.callAsync(param)
        .doOnSuccess(result -> record(args, result, emissions, callTime, param.getRuntimeContext(), elapsed(t0)))
        .doOnError(error  -> recordFailure(args, emissions, callTime, param.getRuntimeContext(), elapsed(t0)))
        .doFinally(signal -> EMISSIONS.remove(use.getId()));
});
```

`ToolInvocation` record 增 `long durationMs` 字段（`ToolInvocation.java:15-23`，追加分量——record 消费方均模式解构/具名访问，编译器兜底改点）。落库时机：**回合结束随轮记录批量写**（§5.3），不在单工具回调里逐条 INSERT。

### 5.2 对话轮级（`ObservabilityAgentHook`，新 hook）

`implements Hook, RuntimeContextAware`（沿 `TrustAgentHook.java:65` 同款注册：`HarnessAgentFactory.build()` 的 builder `.hook(...)` 追加——`HarnessAgentFactory.java:65-66` 现有单 hook 链改双 hook）：

- **时延**：`onEvent` 分派 `PreCallEvent` 记 `System.nanoTime()` 起点（RuntimeContext typed put，随回合传递——`TrustContext` 同款通道）→ `PostCallEvent` 计 `durationMs`。
- **token 累计**：`PostReasoningEvent.getReasoningMessage().getUsage()` 与 `PostSummaryEvent.getSummaryMessage().getUsage()` 各轮累加（`ChatUsage.getInputTokens/getOutputTokens/getCachedTokens`——javap 四值 API；**注意每次模型调用一个 Msg、非整回合聚合**，逐轮累加是唯一正确口径；`emit-token-usage` 是前端 SSE 事件，与落库无关）。轮失败（`ErrorEvent`）计入 failed + `getError()` 摘要。
