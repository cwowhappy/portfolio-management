## 二、测试架构

### 2.1 分层定位（遵守四层分工红线）

> 切片验接线、单测验逻辑、集成验真实依赖、BDD 只锁核心旅程不贪多——**同一行为不跨层重复断言**。
> （`docs/technology/architecture/03-后端测试架构.md:15`）

Agent 测试在四层中的分布与理由：

| 层 | Source Set | Agent 域放什么 | 不放什么 |
|---|---|---|---|
| 单元 | `src/test` | 工具逻辑、工厂分支、纯函数（ChartSpecs）、codec 契约、ThreadLocal 语义 | 任何真实 I/O、Spring 容器、Docker（ArchUnit 强制） |
| 切片 | `src/test` | 装配契约：`AgentConfigContextTest`（`ApplicationContextRunner` 验条件装配） | `@WebMvcTest` 切片——**Agent 不适用**，见 2.6 |
| 集成 | `src/integrationTest` | SSE 全生命周期、HITL 审批、真实 MCP server、stateStore 落盘、PG 种子数据 | 已被单测锁死的纯逻辑分支 |
| BDD | `src/bdd` | 用户级旅程（注册→审核→对话），维持现状 | 技术细节（G8 准入） |

### 2.2 组件选型映射（结合本项目已选组件）

| 测试需求 | 组件 | 本项目用法 |
|---|---|---|
| 单元框架 | JUnit 5（Jupiter）+ AssertJ | 字符串/JSON 断言用子串包含，不引 JsonPath |
| Mock | Mockito 静态工厂风格 | `mock()/when()/verify()` 静态导入，**不用** `@ExtendWith(MockitoExtension.class)`，mock 在 `@BeforeEach`/helper 手动创建 |
| 装配切片 | `ApplicationContextRunner` | `AgentConfigContextTest`，不起 web、不触 Docker |
| 全栈集成 | `@SpringBootTest` + MockMvc + Testcontainers PG | 继承 `PostgresTestSupport`（JVM 单例容器），`@AutoConfigureMockMvc` |
| BDD | Cucumber 中文场景 + `CucumberSpringConfig` 共享上下文 | 假 Model 经 `@TestBean`，全程不打真实 LLM |
| 契约 fixture | 前端 zod fixture 逐字符比对 | `ChartSpecFixtureTest`（`features/chat-rich-content/fixtures/*.json`） |
| 架构守护 | ArchUnit 3 测试类 | 命名/GWT、test 禁 Testcontainers、`*SliceTest` 注解约束 |
| 覆盖率 | JaCoCo 0.8.13 聚合三层 exec | 挂 `check`，BUNDLE 级指令/分支 ≥0.80；agent 包无排除，全额入门槛 |
| 断言质量诊断 | PIT 1.20.2 + Descartes | 现状 targetClasses 不含 agent 包，见 5.3 扩展建议 |

### 2.3 测试替身体系（Agent 特有）

| 被替代物 | 替身 | 接线方式 |
|---|---|---|
| LLM（DeepSeek） | `FixedReplyModel`（固定回复）/ `ScriptedModel`（脚本队列，支持工具调用脚本） | `@TestBean(methodName=...)` 按 bean 名 `investModel` 定义级替换；`DEEPSEEK_API_KEY` 给占位值只为触发条件装配 |
| 行情服务 | mock `OrchestratingMarketDataService` | `@MockitoBean` |
| MCP server | 内嵌 Tomcat + streamable HTTP（真实握手） | JdbcTemplate seed provider/endpoint，`@AfterEach` 清理（教训：seed fixture 必须配套 teardown） |
| PostgreSQL | `PostgresTestSupport` 单例容器 | 继承基座或 `@DataJpaTest + @ServiceConnection` |
| 请求上下文 | `CurrentUserHolder`（ThreadLocal） | 每个测试 finally `remove()`，防跨测试串扰；集成测试关注异步线程下的隔离性（见 4.2-C） |

### 2.4 契约测试原则：钉「线上字节」

- AG-UI 事件序列化以**实际线上字节**为断言对象，不断言内存对象（issue #25 教训：`expiresAt:null` 被前端 zod 拒收）。
- `ChartSpec` 与前端 zod schema 的契约用 fixture 逐字符相等锁定，后端改 spec 字段必须同步改 fixture。
- 工具 emit 的摘要文本（`RUNNING` 等）是前端 e2e 断言锚点，单测锁结构 + 关键字段。

### 2.5 SSE 断言固定模式（集成层统一）

```
perform(POST /agui/run) → andExpect(request().asyncStarted())
→ result.getAsyncResult(30_000) → asyncDispatch(result)
→ 响应体子串 / JsonNode 结构断言
```

### 2.6 为什么 Agent 没有 `@WebMvcTest` 切片

`/agui/run` 端点由 AgentScope agui starter 的 MVC 控制器（`AguiMvcController`）提供，非本项目代码；其自动配置 + SSE 异步模型在切片里无法真实装配。因此 Agent 的 web 入口一律走完整 `@SpringBootTest` 集成测试（已有 4 个类覆盖），web 层单测只测 `InvestAguiRuntimeContextResolver` 这类本项目自有的纯协作类。

**A. `McpClientPoolTest`（新建）** — 补缺口 #1 的单测侧

|---|---|

|---|---|
| `givenConcurrentRunsForDifferentUsers_whenInterleaved_thenEachRunUsesOwnUserId` | 两用户并发 `/agui/run`（`ConcurrencyTestSupport.race()` 齐放），ScriptedModel 记录收到的 toolkit/会话，断言无串扰——`CurrentUserHolder` 在 SSE 异步线程模型下 remove 的时序风险点（`AgentConfig.java:41` finally remove）。注：agentscope 对**同一** `(userId, sessionId)` 的调用天然串行化（`agent.md:184`），本用例并发维度是「不同用户」，同 session 串行语义不在此断言 |

**D. 会话持久化用例（2026-09-15 核实完毕，已裁决列入批次 2）**

核实结论：`AguiStreamIntegrationTest` 仅 3 用例（全量流/未注册/非法体）；`AguiInterrupt` 的 resume 是中断续跑、`AguiChart` 的「两轮」是单次 run 内两帧——**均非跨 run 会话记忆**，ADR-0011 语义此前零测试覆盖。

`server-side-memory: true` 语义＝前端每轮只发最新一条、服务端 stateStore 拼历史。

| 方法名建议 | 断言要点 |
|---|---|
| `givenSecondTurn_whenSendOnlyLatestMessage_thenAgentSeesPriorContext` | 同一 session 两轮，第二轮仅发最新消息，ScriptedModel 第二帧断言输入含第一轮内容（锁 ADR-0011 服务端记忆语义） |

## 五、Agent 效果评估

> 定位（口径已确认）：单元/集成测试回答「**代码对不对**」，效果评估回答「**Agent 表现好不好**」。评估**不进 CI 门禁**——真实 LLM 输出非确定性，挂门禁必 flaky；定位是**周期性诊断仪**：`InvestSystemPrompt` / `AgentConfig` / 工具集变更必跑、发布前必跑。与 `make smoke`（能跑通）互补，关注跑得好不好。

### 5.1 评估手段（已确认）

- **全自动结构断言（主力）**：SSE 事件流上的工具序列/参数/数值比对自动判分，零额外成本
- **LLM-as-judge（补主观维度）**：判分模型用 DeepSeek 自身、温度 0、评分细则（rubric）固化在题库资源里；报告记录 judge 模型与版本。judge 与被评模型同源是小项目务实取舍，未来可换更强评委
- 不做纯人工 checklist 主线

### 5.2 双轨题库（规模已确认：30~50 题）

| 轨道 | 占比 | 数据来源 | 断言深度 |
|---|---|---|---|
| 桩数据题 | ~80% | 复用集成测试 `@MockitoBean` 行情桩，固定工具返回 | 答案中的数值/事实与桩数据自动比对（幻觉自动判） |
| 真实行情题 | ~20% | 真实行情接口 | 只断言结构（工具序列/图表事件/免责声明），数值一致性由 `make smoke` 的 fixture 新鲜度兜底 |

设计要点：固定输入 → 输出断言稳定可自动化；评估的是「给定确定数据，Agent 能不能组织对答案」，而非行情本身。

**场景分布（已确认四类全选）**：

| 场景 | 题量建议 | 评估点 |
|---|---|---|
| 行情单轮问答（个股/大盘/K线/财务） | 12~15 | 工具序列（先 `search_stock` 后查）、实体对齐（「茅台」→ 600519）、双通道完整性、数值保真 |
| 多轮指代消解 | 6~8 | 第二轮承接上一轮实体；锁服务端记忆（ADR-0011）与上下文压缩行为 |
| 边界与拒答 | 6~8 | 非投研问题拒答、免责声明、拒绝后不原样重试（FR-7） |
| MCP 扩展源问答 | 6~8 | 妙想/Tushare/Wind 兜底分工；MCP server 桩（复用 `McpHitlIntegrationTest` 内嵌 Tomcat 模式） |

### 5.3 维度与判分映射

| 维度 | 信号 | 判分方式 |
|---|---|---|
| 工具调用正确性 | `tool_call` 事件序列 | 自动断言 |
| 参数与实体对齐 | `tool_call` args vs 题面实体 | 自动断言 |
| 数据保真（幻觉） | 答案 vs 桩数据/工具返回 | 桩轨自动比对 + 真实轨 LLM-judge |
| 双通道完整性 | 图表事件 + 摘要文本 | 自动断言 |
| 指令遵循 | 免责声明、拒答、不重试 | 规则断言 + LLM-judge |
| 多轮记忆 | 第二轮 `tool_call` 目标 | 自动断言 |
| HITL 行为 | `interrupt` 事件 | 自动断言（抽样 1~2 题） |
| 回答质量（自然度/专业度） | 答案文本 | LLM-judge rubric 细项 |
| 性能/成本 | SSE 时间戳 + `token-usage` | 自动统计 |

### 5.4 实施形态与批次 4

- **位置**：`backend/src/eval/`（独立目录，不进 test/integrationTest/bdd 源集，不污染 JaCoCo 门槛）；题库 YAML + 运行器 + rubric 资源
- **运行方式**：打运行中的后端 `POST /agui/run`（`smoke.sh` 模式），收 SSE → 断言 → 报告
- **报告**：JSON（机读，落盘可追溯）+ Markdown（人读，含各维度得分、失败 case 的事件流回放、与上一次运行的得分对比）；`Makefile` 增 `eval-agent` target
- **评分出口**：结构断言通过率 + LLM-judge 各细项均分；**不设硬门槛**，用差异对比回答「这次改动让 Agent 变好还是变坏」

**批次 4：效果评估框架（真实 LLM，依赖 `DEEPSEEK_API_KEY`）**

1. `backend/src/eval/` 骨架：题库加载器 + SSE 客户端 + 断言器 + LLM-judge + 报告
2. 首批题库 30~50 题（按 5.2 四类分布）+ rubric 资源
3. `Makefile` 增 `eval-agent` target（先起后端或复用运行实例，同 smoke 模式）
4. 基线报告落盘，作为后续对比基准
5. 验证：`make eval-agent` 出报告，人工核对 3~5 条失败 case 的判分是否合理
