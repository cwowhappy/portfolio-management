# 三服务首次发布方案 v1（Ubuntu 直接部署，无 Docker）

> 环境：阿里云 Ubuntu 服务器 + 已有 Nginx（HTTPS）。三个服务以本机进程 + systemd 方式直接部署，不用 Docker。
> 本文是 v1 首次发布的**操作手册**；任务清单、执行顺序、发布门槛与决策记录见 [发布计划.md](发布计划.md)。
> 2026-09-28 修订：迁移口径改为 squash 后单一基线（计划 A1 执行前部署则仍为 V1~V21 逐个执行，其余章节不受影响）；.env 模板补齐 MAIL_*/飞书/prod profile；验收与备份扩充。

## 一、架构

```
浏览器 ─HTTPS─► Nginx(:443) ──► frontend(node :3000)
                                  └─ /api/** 同源反代 → backend(java :8080)
backend ──► postgresql(:5432)
collector(python 定时) ──► postgresql(:5432)
```

- 唯一对外入口是 **frontend**（`/api/**` 由它反代到 backend）；backend/collector 只监听 localhost。
- 三个服务各一个 **systemd 单元**；PostgreSQL 用 apt 自带服务。

## 二、安装运行时（一次性）

```bash
# JDK 21（后端构建 + 运行）
sudo apt install -y openjdk-21-jdk-headless

# Node 22 + pnpm（前端）
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
corepack enable && corepack prepare pnpm@11.22.0 --activate

# Python 3.12（collector）
sudo apt install -y python3.12 python3.12-venv

# PostgreSQL（Ubuntu 24.04 默认 16；更老版本需 PGDG 源）
sudo apt install -y postgresql postgresql-contrib

# 运行用户 + 目录
sudo useradd -r -m -d /opt/invest invest
sudo mkdir -p /opt/invest/{backend,frontend,collector}
```

## 四、构建产物（服务器上 git clone + 构建）

```bash
sudo git clone <仓库地址> /opt/invest/src
cd /opt/invest/src

# 1) 后端双 jar（MS-30 起 make build 产生产 app.jar + 评测 *-eval.jar——
#    evalBootJar 打包 EvalRunner 与题库/rubric 资源，供每晚定时回归子进程执行）
cd backend && sudo ./gradlew bootJar evalBootJar --no-daemon
# build/libs 有 4 个 jar（boot 主 jar / *-eval / *-plain / *-test-fixtures），按用途挑选：
main_jar=$(ls build/libs/*.jar | grep -vE -- '-(eval|plain|test-fixtures)\.jar$')
sudo cp "$main_jar" /opt/invest/backend/app.jar
sudo cp build/libs/*-eval.jar /opt/invest/backend/   # 与 app.jar 同目录分发（jar-path 空时的派生前提）

# 2) 前端 standalone（next.config 已 output: "standalone"）
cd ../frontend && sudo pnpm install --frozen-lockfile && sudo pnpm build
sudo cp -r .next/standalone/. /opt/invest/frontend/
sudo cp -r .next/static /opt/invest/frontend/.next/static
# 仓库当前没有 frontend/public/ 目录（无静态资源），cp 会直接报错——
# 与 frontend/Dockerfile 构建期的 `RUN mkdir -p public` 规避法一致，先建目录占位；
# 后续仓库新增 public/ 静态资源时，此步改为：sudo cp -r public/. /opt/invest/frontend/public/
sudo mkdir -p /opt/invest/frontend/public

# 3) collector venv + 源码
cd ../collector
sudo python3.12 -m venv /opt/invest/collector/.venv
sudo /opt/invest/collector/.venv/bin/pip install -r requirements.txt
sudo cp -r collector migrations tasks /opt/invest/collector/

sudo chown -R invest:invest /opt/invest
```

> **生产禁设清单**（出现在 .env 即配置事故）：`MAIL_TEST_FIXED_CODE`、`MAIL_TEST_MODE`（测试固定码——设了固定码未开测试模式后端直接拒启动，开了则是假绿）；`E2E_DEV_SEED`、`E2E_HITL_MCP_URL`（e2e 专用，会向生产库灌样例数据）；`Eval_MODE`（MS-30 eval 子进程专用开关——生产进程设 `Eval_MODE=true` 会让 `SchedulingConfig` 整体不装配，**全部定时任务**（原则预警/证伪扫描/清理/eval 调度）静默停摆）。
> 可选项说明：`FEISHU_API_BASE`（默认 `https://open.feishu.cn`）、`COLLECTOR_ALERT_WEBHOOK`（通用 JSON 告警逃生通道）一般无需设置；完整变量语义见根 README 配置表。

## 六、systemd 三个单元

**`/etc/systemd/system/invest-backend.service`**

```ini
[Unit]
Description=Invest Agent Backend
After=network.target postgresql.service

[Service]
User=invest
WorkingDirectory=/opt/invest/backend
EnvironmentFile=/opt/invest/.env
Environment=SPRING_PROFILES_ACTIVE=prod

RestartSec=5

[Install]
WantedBy=multi-user.target
```

## 八、启动 + 迁移

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now invest-backend invest-frontend invest-collector
sudo systemctl status invest-backend invest-frontend invest-collector --no-pager
```

**首次启动自动完成**：backend Flyway 建全部业务表（squash 后为单一 `V1__baseline.sql`，含全部 30+ 张表、MCP 三表与 skill 配置表的 seed、行业链示例种子；合并前的历史口径为 V1~V21 共 22 个迁移逐个执行，对全新空库结果一致）+ `AdminSeedRunner` 按 `.env` 的 `ADMIN_*` 种子管理员；collector 启动序列自动执行 `alembic upgrade head` 建采集运维表 → 刷交易日历 → `tasks/*.yaml` 登记 17 个采集任务 → BlockingScheduler 开始调度（交易日门控 + advisory lock 防重，冷启动对从未成功任务立即补跑一次）。

> **Skill 系统无需部署动作**：内置 `tushare_data` / `wind_finance` 两个 Skill 以 classpath 资源随 app.jar 分发，建表后用户即可在前端 `/settings/skills` 启停。

## 十、MCP 数据源 token 填充（部署后手工步骤）

三个内置 MCP provider（妙想 / Tushare / Wind）的 token **不随迁移进 git**——基线迁移（原 V10）仅 seed `NULL` 占位。**P1-10（2026-10-03 交付）后推荐走 admin UI**：先在后端 `.env` 设置加密主密钥，再由管理员登录 `/admin` 页「MCP 数据源 Token」逐个填入（明文仅经请求体一次，服务端 AES-256-GCM 加密落库，界面与 API 均不回显）：

```bash
# 1. 生成主密钥并写入后端 .env（base64 32 字节；缺失不阻断启动，仅设置 token 时报 503）
openssl rand -base64 32   # 输出追加为：MCP_SECRET_KEY=<该输出>
# 2. 重启后端使密钥生效，浏览器以管理员登录 → /admin → 「MCP 数据源 Token」逐个保存
# 3. 填好后可跑手动握手冒烟（initialize + tools/list，token 从环境变量读、未设置的 provider 自动跳过）：
MX_DS_TOKEN=你的妙想token TUSHARE_TOKEN=你的tushare_token WIND_TOKEN=你的wind_token \
  bash /opt/invest/src/backend/scripts/mcp-smoke.sh
```

- token 更换后需重启后端生效（`McpClientPool` 按端点缓存客户端，非目标：自动 evict）。
- **SQL 明文直填降为兼容回退**（存量明文直读仍支持，后端按 provider 记一次 warn 日志）：

```bash
sudo -u postgres psql invest <<'SQL'
-- 妙想走 HEADER em_api_key；Tushare / Wind 走 Bearer。code 值与基线 seed 一致。
-- 仅应急/迁移期使用；填后建议尽快经 admin UI 覆写为密文。
UPDATE mcp_provider SET auth_secret_enc = '你的妙想em_api_key' WHERE code = 'mx-ds';
UPDATE mcp_provider SET auth_secret_enc = '你的tushare_token'  WHERE code = 'tushare';
UPDATE mcp_provider SET auth_secret_enc = '你的wind_ak_token'  WHERE code = 'wind';
SQL
```

- provider 由用户在前端 `/settings/mcp` 自行启用（工具级开关；不支持自定义 server），token 只需部署侧填一次。

## 十二、eval 定时回归与观测看板（MS-30，部署后核对项）

**eval 定时回归**（§四 双 jar + §五 `INVEST_EVAL_*` 配好后自动生效）：每晚 02:17 后端经 `EvalScheduler` 拉起 `*-eval.jar` 子进程全量跑 64 题（同 PG 实例独立 `eval_schema`，每轮 DROP-CASCADE 重置，不动主库数据）；收割后相对回归判定，超阈值经 `AlertNotifier` 推飞书（未配置飞书则降级邮件，均未配置仅留痕 `eval_run` 表）。admin 也可 `/admin` 观测看板手动触发（进行中 409）与 baseline 人工确认。

**部署后人工核对项**（首跑观察清单，一次性）：

1. **jar 派生路径**：`INVEST_EVAL_JAR_PATH` 留空时调度器在生产 jar 同目录派生唯一 `*-eval.jar`——首跑日 02:17 后看日志确认派生路径正确（`journalctl -u invest-backend | grep -i eval`）；若派生失败或同目录多份 eval jar 会 503/报错留痕。
2. **首晚 eval 跑通**：次日核对 `eval_run` 表最新行 `status=COMPLETED`（首跑无 baseline，`alert_status=NONE` 属预期）：`sudo -u postgres psql invest -c "SELECT id,status,alert_status,total_pass,total_fail FROM eval_run ORDER BY id DESC LIMIT 3"`。
3. **停机 RUNNING 行清扫**：后端停机/崩溃若恰逢 eval 子进程执行中，收割缺席会在 `eval_run` 留 `RUNNING` 行（不会自愈），人工清扫：`UPDATE eval_run SET status='FAILED' WHERE status='RUNNING' AND started_at < now() - interval '4 hours';`。
4. **观测看板有数**：浏览器 `/admin` 观测看板——发几轮对话后 trace 表出行、成本/时延图有曲线、版本链含五类资产（首条对话即产生轮观测）。

**CI 冒烟（smoke.yml）**：合并 main 后 GitHub Actions 每日北京时间 09:37 自动跑 `make smoke`（schedule 仅对默认分支生效；推送期可用 workflow_dispatch 手动触发验证一次）。前置：repo secrets 已配置 `DEEPSEEK_API_KEY`（Actions → Settings → Secrets and variables → Actions 核对）。首跑观察：runner 到东财/腾讯行情源的可达性（GitHub 托管网络出口），失败先看 job 内「失败诊断」步骤的双端日志尾段。
