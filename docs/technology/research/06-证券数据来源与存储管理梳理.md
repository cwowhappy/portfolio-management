## 一、全景：证券数据的四条链路

系统内证券数据并非单一路径，而是**四条并行链路**，职责分工明确：

| 链路 | 数据形态 | 是否落库 | 主要消费方 |
|---|---|---|---|
| **A. Collector 批量采集** | 日频快照/历史序列（估值、行情、ETF、国债、行业、财务） | 是，10 张 PG 表 | 估值域、筛选域、收益分析、行业研究（后端只读） |
| **B. Backend 实时直连** | 实时行情/K线/搜索/财务/新闻/大盘 | 否（仅进程内 TTL 缓存） | 前端行情组件、Agent 10 个 @Tool、组合市值、健康探活 |
| **C. MCP 对话内实时** | 公告/研报/EDB/港美股/期货等机构级数据 | 否 | Agent 对话（用户级启停） |
| **D. 混合链路** | 财务 = 落库表 + live 两源并列透传（非值合并）；组合市值用实时行情 | 部分 | 财务分析（杜邦）、持仓市值 |

```
外部上游                    采集/编排                       存储                消费
─────────                ──────────────                ─────────           ─────────
tushare pro ──┐          collector (Python)            postgres:16         backend 各域服务
akshare ──────┤  17 YAML 任务 / APScheduler   ──upsert──▶ 10 业务表 ──读──▶ (估值/筛选/收益/行业)
东财移动端 ────┘  熔断·重试·校验                     + 4 运维表
                                                    ▲
腾讯 ─────────┐          backend (Java)              │ schema DDL
东财 push2 ────┼─ 三级降级编排 ──▶ TtlCache(进程内)   │ (Flyway 契约)
新浪 hq ──────┘   实时不落库                          │
                                                    │
MCP 三家(妙想/Tushare/Wind) ──▶ 对话内实时，不落库      │
                                                    │
财务: tushare 落库表 + 东财 live ── FinancialQueryService 合并
```

## 三、数据获取方式

### 3.1 Collector：声明式任务 + 插件源（链路 A）

**任务契约**：YAML（collector/tasks/，17 个）→ seed upsert 进 `collector_task`（缺键/未知键 fail-fast，jobs.py:72-80）→ 装配执行（jobs.py:95-113）。字段封闭为 `TASK_COLS`（repositories/tasks.py:3-16）：source_ids（**有序备源列表**）、converter（12 套字段映射，jobs.py:162-275）、calc、validator、target_table、schedule、trading_day_gated、retry_max、retry_backoff。

**任务总表**（全部 enabled，retry_max=3 exponential；cron 时区 = 容器 TZ=Asia/Shanghai，docker-compose.yml:62）：

**执行管线**（executor/executor.py:66-170）：selector 按健康分排序候选源 → 逐源 fetch（SourceError 换下一源）→ convert（列映射+强转，**转换失败静默置 None**，converters/field_mapping.py:7-29）→ **先校验后 calc**（min_rows 基于明细行数）→ 统一 setdefault trading_day → store.upsert。

**可靠性机制**：
- 调度：APScheduler 3.11 BlockingScheduler，每任务 coalesce=True / max_instances=1 / misfire_grace_time=3600（jobs.py:141-149）；**从未成功的任务冷启动补跑**（jobs.py:137-140）。
- 互斥：PG advisory lock `pg_try_advisory_lock(hashtextextended(task_code,0))`（scheduler/runner.py:18,66-72），跨进程防重。
- 重试：仅 AllSourcesFailed/StoreError 触发，3 次指数退避 30×2ⁿ 秒（runner.py:49-94）。
- 熔断：连败≥3 open 600s；健康分=100×成功率−延迟惩罚−连败惩罚（executor/selector.py:5-23）。注意熔断按**任务运行**计而非尝试计（runner.py:78）。
- 限频：线程安全最小间隔限速器（sources/ratelimit.py:12-28），常量按上游实测钉死（如 fina_indicator 200 次/分 → 0.35s）。
- 可观测：执行前插 running 行、终态回填（runs.py:26-113），异常逃逸兜底置 failed。
- **无通用 fetch 超时**（executor 层不包裹；唯一超时是 ETF detail 15s，plugins.py:274）。

**backfill**（backfill.py:5-16）：仅 CLI，`--start/--end` 必填；**拒绝 supports_range=False 的源** → etf_basic / shenwan_mapping / stock_financial / etf_tracking_error / industry_valuation_backfill / all_a_valuation **均不可回补**；无独立断点续传（可靠性=源区间拉取+upsert 幂等重跑覆盖，无分片、无进度持久化）。

### 3.2 Backend：实时直连三级降级（链路 B）

链路：`前端/Agent → MarketController(/api/market/*) 或 InvestTools(10 个 @Tool，agent/InvestTools.java:55-266) → CachedMarketDataService（缓存装饰器）→ OrchestratingMarketDataService（降级编排）→ 腾讯/东财/新浪客户端`。

- 降级矩阵（OrchestratingMarketDataService.java）：实时行情 腾讯→东财→新浪（:77-86）；K线 腾讯→东财（:95-98）；指数 腾讯→东财→新浪（:172-180）；**搜索/财务/新闻仅东财单源**；东财 PE/PB 缺失时用财务指标自算 TTM 估值（:104-142）。
- 保护：共享 HttpClient（强制 HTTP/1.1）+ RateLimiter 5 req/s，3s/5s 超时、3 次重试退避 300ms（MarketConfig.java:15-28，application.yml:70-76）。
- 缓存：进程内 TtlCache（有界 LRU+惰性过期，infrastructure/cache/TtlCache.java:16-67），TTL 分级 quote/overview 15s、kline/news 5m、search 10m、financials 1h（application.yml:77-84）；应用级缓存（估值/筛选/探活）默认 1000 条 5min（CacheConfig.java:13-15）。**无主动失效，全靠 TTL；无 Redis**（build.gradle 无依赖、compose 无服务）。
- 混合链路：财务 = stock_financial 库表 + 东财 live 两源**并列透传**（非值合并；杜邦是唯一混合口径点——netMargin 取 live 最新期、roa/debt/roe 取库表 latest，采集窗口内可能不同报告期，P1-11 已注记），live 失败降级仅库表（FinancialQueryService.java:13-51）；组合市值走实时 quoteBatch（application/portfolio/PortfolioApplicationService.java:456）；健康探活真实拉 600519 行情测延迟（HealthController.java:54-78）。

### 3.3 MCP：对话内实时（链路 C）

DB 配置三表（mcp_provider/mcp_endpoint/mcp_user_config，V10__mcp.sql:2-36）驱动，按用户装配启用 provider 的工具（UserToolkitFactory.java:47-59）；客户端按 endpoint 缓存不失效（McpClientPool.java:23-38）；**端点失败仅 log.warn 静默降级**。与 collector 互补不冗余：MCP 供对话内机构级数据，A 股行情/估值走内置工具+落库。`config/mcporter.json` 只配本地浏览器自动化 agent，与运行时无关。

## 四、存储管理

### 4.1 拓扑

PostgreSQL 16 单库（compose `db` 服务；本地 dev 连 Homebrew postgres）。collector 写 / backend 读同一 schema。**无 Redis、无消息队列、无对象存储**——任务互斥用 PG advisory lock，缓存全进程内。

### 4.2 迁移双轨契约（关键设计）

- **业务表 DDL 全部归 backend Flyway**（V1-V20），V13 头注明确："本 schema 为 collector 写入、后端读取的跨服务契约"（db/migration/V13__analytics_close.sql:1）。
- collector Alembic 仅建 4 张运维表（migrations/versions/0001_ops_tables.py）：collector_task / collector_task_run / collector_source_health / trading_calendar。
- 部署顺序：collector depends_on backend healthy（docker-compose.yml:63-67）保证业务表先建；collector 启动自动 alembic upgrade head（jobs.py:365-367）。

### 4.3 表清单与读写方（14 张）

| 表 | 业务键（UNIQUE/PK） | 写方 | 读方（backend） |
|---|---|---|---|
| valuation_snapshot | trading_day | all_a_valuation | ValuationRepositoryImpl:44-61 |
| industry_valuation | (trading_day, industry_code) | industry_valuation + backfill | 同上:64-66 |
| index_valuation_history | (trading_day, index_code) | index_valuation | 同上:74-76 |
| treasury_yield_curve | (trading_day, term) | treasury_yield_curve | RiskFreeRateAdapter（1Y）/ValuationRepo（10Y） |

| index_constituent | (index_code, stock_code) | index_constituent | ScreeningRepositoryImpl:83 |
| stock_valuation_daily | (trading_day, stock_code) | stock_valuation_daily | 收盘价适配/估值/筛选 |

### 4.4 写入语义

每表一条手写 `INSERT ... ON CONFLICT (业务键) DO UPDATE`（store/writer.py:5-79），幂等可重跑；唯一例外 index_constituent 同事务先删后插（快照语义，writer.py:137-143）；etf_basic 更新显式不触碰 tracking_error_1y（:68-78）。executemany 一次提交**无分块**（:134-144，5k 行 smoke 亚秒级）。TABLE_COLUMNS 与 UPSERT_SQL 双定义有一致性测试兜底（tests/test_writer_consistency.py）。**无分区、无归档、无 TTL**。

### 4.5 校验

check 类型 min_rows/required/not_null/type/range/unique/allowed_values（validators/rules.py）；失败二分：hard=整批拒绝+换源+重试（**防脏数据进库**），soft=剔行+partial（框架能力，**现役 YAML 全 hard 未启用 soft**）；无独立告警通道，出口只有 run 记录与日志。**无日期连续性校验、无跨表一致性校验**。

## 五、优势

1. **跨服务 schema 契约清晰**：迁移双轨+V13 头注声明+双定义一致性测试+conftest 按 Flyway/Alembic 双轨建 schema（tests/conftest.py:30-97），collector 与 backend 职责边界（写/读）在代码与部署顺序上都有强制。
2. **幂等写入设计**：唯一约束+upsert 全覆盖，任务重跑、backfill 重跑、冷启动补跑都安全；tracking_error 全量重算也幂等。
3. **多级降级成熟**：collector 侧有序备源+熔断健康分；backend 侧腾讯→东财→新浪三级编排+估值自算兜底；MCP 静默降级。单上游故障不中断服务。
4. **先校验后入库**：min_rows hard 整批拒绝（如 all_a/stock_valuation_daily min_rows=1000），防上游异常返回少量脏数据污染落库。
5. **全程可观测落库**：collector_task_run 记录每次执行（含 skipped/partial）、collector_source_health 记录健康分；启动时 staleness 检查（阈值 15 天，jobs.py:57,370-372）。
6. **声明式任务+fail-fast**：YAML 契约字段封闭，seed 时未知键即报错；17 个 YAML 有装配冒烟测试（tests/test_yaml_assembly.py）。
7. **测试面广**：31 个测试文件覆盖全部包内模块，含真实 PG 集成（testcontainers）、双实现一致性（行业重算 vs calc）、性能 smoke。
8. **实时/批量分工明确**：页面与 Agent 的实时需求走直连+短 TTL 缓存，历史分析走落库表——没有把实时接口当日志库用，也没有为历史分析反复打实时源。
9. **决策有据可溯**：research/01/02 基于实测记录了 87 次接口验证、放弃项及原因（legulegu 硬故障、财新 404、tushare news 无权限、bond_zh_us_rate 静默漏采 bug 的发现与修复）。

## 六、劣势与风险

### 6.1 采集侧

1. **tushare 依赖集中**：17 任务中 11 主源+1 备源走 tushare，token 单一（env 一把钥匙）；积分等级/限频政策一变，估值、行情、ETF、成分、财务全链路同震。逐股日快照（stock_valuation_daily）**无备源**——akshare 备源只覆盖 all_a 聚合快照。
2. **无通用 fetch 超时**：executor 不包裹超时（executor.py:93），akshare/tushare SDK 内部超时未配置；上游挂起可长时间占用 APScheduler 默认线程池（未显式配置大小）。
3. **无主动告警**：任务 failed/partial、validator 拒批只有 run 表+日志；与遗留项 MS-15（SMTP）一致，数据断流靠人发现。
4. **backfill 能力弱**：仅 range 源可回补、无断点续传/分片/进度持久化；6 个任务（含 stock_financial）不可回补，历史缺口只能靠源端全量重拉。
5. **硬编码密集**：指数/行业码表（plugins.py:30,122,148-180）、H11001/518880、ETF URL+headers、期限表、2006 起点、各限速常量全部在代码内，无配置出口；上游变更需发版。
6. **静默数据质量缺口**（复核确认）：①指数股息率是近似值（权重×dv_ttm），**任一步失败回退 0.0 且无标记**（plugins.py:1219-1233）——而 ERP=沪深300股息率−10Y 国债（09-估值域），回退值直接污染 ERP 输入；②converter 数值强转失败静默置 None；③ETF enrich 单只失败置 null 无计数上报；④无日期连续性/跨表一致性校验（营收补数教训正属此类）。
7. **rows_written 监控口径失真**：etf_tracking_error 的 UPDATE 在 fetch 内完成、fetch 恒返空帧，rows_written 恒 0，按此监控会误判"没干活"。（2026-09-27 实施期修正：industry_valuation_backfill 返回真实 DataFrame 走 writer upsert、rows_written 本就准确，稳态 0 行=无缺失语义正确，原报告把它并列为恒 0 有误。）
8. **etf_basic 周任务脆弱**：逐只裸 HTTP+UA/Referer 伪装，全量 ~16 分钟；接口改版即断，单只失败静默。
9. **trading_day 隐式契约**：executor 对缺 trading_day 的记录 setdefault 今天（executor.py:114-116），backfill 场景源漏列会被静默改成当天——当前无 bug 但脆弱。

### 6.2 存储侧

10. **缓存全进程内、无 Redis**：重启即冷启动；估值/筛选缓存无法跨实例共享（当前单实例是合理取舍，但这是多实例化的硬前提）。
11. **无容量规划触发器**：stock_valuation_daily 全A日快照 ~5.4k 行/日，年增 ~135 万行；当前量级 PG 无压力，但没有任何"何时分区/归档"的预案。
12. **双轨迁移协调成本**：业务表 schema 演进必须 backend Flyway 发版，collector 无法自主改表；契约靠头注约束，字段口径变更无机器校验。
13. **无连接池**：TaskRunner 每次尝试新建连接（runner.py:63-65），源侧同样（jobs.py:282-283）；当前频率无碍，扩展时是隐患。
14. **时区隐式契约**：cron 语义依赖容器 TZ=Asia/Shanghai（compose env）；本地裸跑随宿主时区，跨环境部署有偏移风险。

### 6.3 实时链路侧

15. **搜索/财务/新闻东财单源**：这三类无降级路径（OrchestratingMarketDataService 仅行情/K线/指数有编排）。
16. **财务两源口径漂移风险**：stock_financial（tushare 季频）与东财 live 同指标口径未必一致，FinancialQueryService 合并时未标注来源口径差异。
17. **MCP 安全项未接线**：token 明文存 DB、tool-timeout/pool-max-size 声明未生效、token 更新需重启（05 文档自认，复核仍成立）。

### 6.4 文档侧

18. 数处文档漂移（明细见第八节），集中在"文档写的是设计意图、代码已演进"的场景。

## 七、优化建议

### P0：低成本高收益（近期，多数不涉及架构）

1. **executor 通用 fetch 超时**：YAML source 项加 `timeout_seconds`，executor 用线程/信号包裹；先覆盖长耗时源（etf_basic、stock_financial）。
2. **任务终态 webhook 告警**：runner 终态 failed/partial 时回调 webhook（钉钉/企微/Slack 任一），与 MS-15 SMTP 打通后升级邮件；改动点集中在 runner.py 终态回填处。
3. **日终数据新鲜度巡检**：新增轻量任务对每张业务表 `max(trading_day)` 与 trading_calendar 对账（交易日+1 中午仍未更新即告警）——直接对应"营收列静默缺数靠 e2e 才发现"的教训，把 staleness 检查从"仅启动时"（jobs.py:370-372）变为每日。
4. **股息率近似值显式标记**：index_valuation_history 加 `dv_estimated BOOL`（或 run.message 记录），回退 0.0 时置位；ERP 读侧据此告警/降级。同时修正"回退 0.0"为"回退 NULL+上一有效值"，避免 0 值参与分位计算。
5. **rows_written 口径修正**：etf_tracking_error 挂 Source.last_affected_rows 上报实际影响行数，经 rows_affected 列（Alembic 0002）落 run 记录，监控不再失真。

### P1：中期（结构性改进，可排期）

6. **码表/限速/URL 外置**：指数行业码表、限速常量、东财 URL 迁入 YAML params 或 config，硬编码降为零散常量的最小集。
7. **backfill 增强**：range 源按月分片+进度表（记录已完成区间，失败可续）；快照型任务（etf_basic/shenwan_mapping）本就幂等，可加"按日循环重放"模式补历史。
8. **etf_basic enrich 改造**：并发化（受限于 0.3s 礼貌间隔可保持）+失败计数上报进 run.message；中期寻找批量接口替代逐只爬移动端。
9. **stock_valuation_daily 补备源**：参考 research/02 已验证接口（akshare 组合或东财 datacenter）做第二落库源，消除逐股快照单源风险。
10. **MCP 安全接线**：token 加密存储（复用后端已有加密设施）、tool-timeout/pool-max-size 参数生效——文档自认项落地。
11. **财务两源口径文档化**：FinancialQueryService 合并处标注两源口径与优先级，防止后续维护者误当同口径。

### P2：战略/触发式（明确"何时才做"，防止过度设计）

12. **分区/归档**：设定触发阈值（如 stock_valuation_daily >3000 万行或查询 P95 恶化）再按年分区/冷数据归档；**当前不动**。
13. **Redis 引入**：仅在多实例部署或跨进程缓存共享需求出现时；单实例下进程内 TtlCache 是正确取舍，**当前不引入**。
14. **数据目录活文档**：把本篇第二/四节的"源→任务→表→消费方"映射转为 docs 下的活文档（data catalog），每次加任务/表时同步——比散在各模块文档里更难漂移。
15. **明确不引入时序库/数据湖**：量级（日增万行级）不支持该复杂度，PG+索引+（远期）分区足够；写明以防未来过度设计。
