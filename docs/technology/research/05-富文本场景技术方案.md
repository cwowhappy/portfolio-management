## 0. TL;DR

1. **总体路径**：行情工具返回结构化 **ChartSpec/TableSpec JSON** → `TOOL_CALL_RESULT.content`（SSE）→ 前端 `useRenderTool` 按工具名匹配 → ECharts/TanStack Table 渲染卡片。文字仍走 `TEXT_MESSAGE_*` + react-markdown（现状），图片走 markdown `![](url)` + 定制 img 组件。
2. **双通道（本方案核心二开点）**：采用**方案一「`ToolEmitter.emit` 发全量 + 返回摘要」**——字节码级已核实：emit 的块只进 SSE 事件流**永不进 LLM/memory**，emit 过的工具其返回值 delta 被 skipSet 跳过。图表全量 JSON 不耗模型 token，LLM 只看摘要。
3. **两个前置必修项**：① `ThreadArea.tsx:212` 调 `renderToolCall` 未配对 toolMessage → 后端工具卡片**永远停在 inProgress、result 不可达**（现状缺陷，图表渲染器的前置依赖）；② `InvestTools` 全部返回 String，会被 Jackson **二次序列化**（`"\"{\\\"code\\\"...}\""`），改 `ToolResultBlock` 返回。
4. **新增依赖**：`echarts@6.1.0`（按需引入，四图+dataZoom 实测 gzip **218KB**）+ `@tanstack/react-table@9.2.4`（**v9 已换代**：`useTable`+`tableFeatures`，非 v8 的 `useReactTable`）。**不装** echarts-for-react（自写 ~60 行 hook）与 react-virtual（几十行不需要）。
5. **待决策**：历史持久化当前丢弃 toolCalls（ADR-0004）→ 刷新/切线程后图表卡片**不重放**。本期建议接受此限制，回放作为二期增强（§7.1）。

## 二、数据契约：ChartSpec / TableSpec

双端对齐的判别联合 JSON。**前端 zod schema 是唯一权威**（渲染器校验入口），Java record 与之一一对应；带 `specVersion` 演进。

### 2.1 前端 zod（`frontend/lib/chart-spec.ts`）

判别联合的每个 member **完整携带** `specVersion`/`type`/`title`/`subtitle`（勿用 `.and()` 交集包一层——zod 对 intersection + discriminatedUnion 的类型推断差且外层 enum 与内层 literal 冗余；P1 Task 2 落地即此写法，先含 pie/bar/line，candlestick/table 随聊天流阶段补全）：

```ts
import { z } from "zod";

export const ChartSpecSchema = z.discriminatedUnion("type", [
  z.object({
    specVersion: z.literal(1),
    type: z.literal("line"),
    title: z.string(),
    subtitle: z.string().optional(),
    categories: z.array(z.string()),                    // x 轴类目
    series: z.array(z.object({                          // 一条或多条线
      name: z.string(),
      data: z.array(z.union([z.number(), z.null()])),   // null = 缺口（recharts 迁移需求：估值序列有缺失日）
      area: z.boolean().optional(),                     // 面积填充
    })),
    unit: z.string().optional(),                        // y 轴单位（如 "%"）
  }),
  z.object({
    specVersion: z.literal(1),
    type: z.literal("bar"),
    title: z.string(),
    subtitle: z.string().optional(),
    categories: z.array(z.string()),
    series: z.array(z.object({ name: z.string(), data: z.array(z.union([z.number(), z.null()])) })),
    horizontal: z.boolean().optional(),                  // 横向条形
    unit: z.string().optional(),
  }),
  z.object({
    specVersion: z.literal(1),
    type: z.literal("pie"),
    title: z.string(),
    subtitle: z.string().optional(),
    data: z.array(z.object({ name: z.string(), value: z.number() })),
    unit: z.string().optional(),
  }),
  z.object({
    specVersion: z.literal(1),
    type: z.literal("candlestick"),
    title: z.string(),
    subtitle: z.string().optional(),
    symbol: z.string(),                                  // "600519 贵州茅台"
    period: z.string(),                                  // "day"|"week"|"month"（与工具入参一致）
    dates: z.array(z.string()),                          // 交易日
    klines: z.array(z.tuple([z.number(), z.number(), z.number(), z.number()])),
    //                        ⚠ 顺序 = [开, 收, 低, 高]（ECharts 官方约定，echarts-examples candlestick-sh-2015.ts 实证）
    volumes: z.array(z.number()).optional(),             // 成交量副图
    mas: z.array(z.object({ name: z.string(), data: z.array(z.union([z.number(), z.null()])) })).optional(), // MA 线后端算好；null = 预热缺口，与 dates 对齐（P2 修正：MA 前 window-1 个点必然缺失）
  }),
  z.object({
    specVersion: z.literal(1),
    type: z.literal("table"),
    title: z.string(),
    subtitle: z.string().optional(),
    columns: z.array(z.object({
      key: z.string(), label: z.string(),
      align: z.enum(["left", "right", "center"]).optional(),
      sortable: z.boolean().optional(),                  // 默认 true
    })),
    rows: z.array(z.record(z.string(), z.union([z.string(), z.number(), z.null()]))),
    defaultPageSize: z.number().optional(),              // 卡片内表格可视高度
  }),
]);
export type ChartSpec = z.infer<typeof ChartSpecSchema>;
// 2026-09-11 澄清：单一契约，table 是变体之一；TableSpec 等只是类型别名（不建独立 schema）
export type TableSpec = Extract<ChartSpec, { type: "table" }>;
export type CandlestickSpec = Extract<ChartSpec, { type: "candlestick" }>;
```

### 2.2 Java 侧（`backend/.../agent/chart/ChartSpec.java`）

```java
/** 与前端 lib/chart-spec.ts 对齐的判别联合；序列化经 ToolResultBlock output TextBlock。 */
public sealed interface ChartSpec permits Line, Bar, Pie, Candlestick, Table {
  int specVersion();          // 恒 1
  String type();              // "line"|"bar"|"pie"|"candlestick"|"table"
  String title();
  String subtitle();          // 可空，序列化时 NON_NULL

  record Line(String title, String subtitle, List<String> categories,
              List<Series> series, String unit) implements ChartSpec { /* type()="line" */ }
  record Series(String name, List<Double> data, Boolean area) {}
  record Bar(String title, String subtitle, List<String> categories, List<Series> series,
             Boolean horizontal, String unit) implements ChartSpec {}
  record Pie(String title, String subtitle, List<Slice> data, String unit) implements ChartSpec {}
  record Slice(String name, Double value) {}
  record Candlestick(String title, String subtitle, String symbol, String period,
                     List<String> dates, List<Kline> klines, List<Long> volumes,
                     List<MaLine> mas) implements ChartSpec {}
  record Kline(double open, double close, double low, double high) {}  // ⚠ 顺序=[开,收,低,高]
  record MaLine(String name, List<Double> data) {}
  record Table(String title, String subtitle, List<Column> columns,
               List<Map<String, Object>> rows) implements ChartSpec {}
  record Column(String key, String label, String align, Boolean sortable) {}
}
// 序列化：JsonUtils.getJsonCodec().toJson(spec)——record+Jackson 需手动保证 type/specVersion 字段
//（建议显式 record 组件或在 builder 里写入，勿依赖类名推断）。
```

契约纪律（进入 backend ArchUnit/单测 + 前端 vitest 双端钉住）：
- 数字一律用 JSON number（Java `double/long`，勿用 `String` 包数字——表格列对齐/排序依赖类型）；
- 空集合省略（`@JsonInclude(NON_NULL)` 语义对齐），前端 zod `.optional()`；
- `specVersion` 不匹配/解析失败时渲染器降级为折叠 JSON 文本卡（不崩聊天流）。

## 三、后端 AgentScope 层（含二次开发）

### 3.1 现状问题（javap 核实）

1. **String 返回值双重序列化**：`DefaultToolResultConverter` 对非 `ToolResultBlock` 返回值一律 `JsonUtils.getJsonCodec().toJson(value)` → `TextBlock(json字符串)`。返回 `String`（当前 `InvestTools` 7 个工具全部如此）会被 `ObjectMapper.writeValueAsString` 再包一层引号转义。〔jar：`io.agentscope.core.tool.DefaultToolResultConverter.convert`；`JacksonJsonCodec.toJson`〕
2. **全量 JSON 进 LLM**：返回值构造的 `Msg(role=TOOL)` 整体进 AgentState/stateStore（`server-side-memory: true`），下一轮 formatter `convertToolResultToString` 只读 output 文本——即工具返回的全量 JSON **逐字进模型上下文**。〔`ReActAgent$CallExecution.notifyPostActingHook`、`AbstractBaseFormatter.convertToolResultToString`〕

### 3.2 双通道方案一（推荐，机制字节码级核实）

`ToolEmitter` 的语义（官方 javadoc 原文）："These streaming chunks are delivered to registered hooks via `onActingChunk()` events but are **NOT sent to the LLM**. Only the final return value of the tool method is sent to the LLM as the tool result."

且 `emitToolResultDelta` 开头有 `if (skip.contains(toolCallId)) return;`——**emit 过非空 output 的工具，其返回值不再产生 SSE delta**。两者叠加 = 天然双通道：

```java
@Tool(name = "get_kline", description = "查询股票K线（返回图表数据）",
      readOnly = true, concurrencySafe = true)
public ToolResultBlock getKline(
        @ToolParam(name = "code", description = "股票代码，如 600519") String code,
        @ToolParam(name = "period", description = "周期：daily/weekly") String period,
        @ToolParam(name = "limit", description = "根数，默认 120") Integer limit,
        ToolEmitter emitter) {                       // 自动注入（无 @ToolParam 的 ToolEmitter 参数）
    KlineData d = marketService.kline(code, period, limit);
    // ① SSE 全量：emit 的 output 累积成 TOOL_CALL_RESULT.content，只走事件流
    emitter.emit(ToolResultBlock.builder()
            .output(TextBlock.builder().text(toJson(ChartSpecs.kline(d))).build())
            .build());
    // ② LLM 摘要：返回值只进 Msg/stateStore；delta 已被 skipSet 跳过，不会混入 SSE
    return ToolResultBlock.text(d.summaryText());    // 如 "600519 日K 120根：最新1850.0，区间[1720.0,1920.0]"
}
```

已核实的保证与注意：
- 全量 JSON 只在 SSE 流过境，**不进 stateStore、不进 LLM**；摘要进 LLM 与落盘（磁盘/上下文双省）；
- 只 emit **一次**含全量的块（多次 emit 的文本会**拼接**进 content）；
- 返回 `ToolResultBlock` 而非 String（避免二次包装）；
- `metadata-only` 的 emit（如官方示例 `progress`）不产生 SSE 事件也不进 LLM，仅 hook/日志可见——进度场景可用；
- **审批续跑轮不回放工具结果**：`hasStartedToolCall` 要求同一 run 内发过 `TOOL_CALL_START`，HITL resume 轮抑制工具事件（04 §3.5/实测注记）。行情工具 readOnly 不走审批不受影响；**未来若给写工具配图表，审批后的续跑轮看不到图**——需在方案层面规避（写工具只回文本摘要）。

### 3.3 方案二（备选）：metadata 载全量 + Enricher 重建 content

```java
// 工具：output=摘要（LLM 只见此），metadata=全量（默认两路都不去）
return ToolResultBlock.builder()
        .output(TextBlock.builder().text(summary).build())
        .metadata(Map.of("chartSpec", fullJson)).build();
```

```java
@Bean
AguiEventEnricher chartSpecEnricher() {          // source=ToolResultEndEvent 携带最终 block 的 metadata
  return (source, events, ctx) -> events.stream().map(e ->
      e instanceof AguiEvent.ToolCallResult t
          && source instanceof ToolResultEndEvent end
          && end.getMetadata() != null
          && end.getMetadata().get("chartSpec") instanceof String full
        ? AguiEvents.withBaseProperties(
              new AguiEvent.ToolCallResult(t.threadId(), t.runId(), t.toolCallId(),
                                           full, "tool", t.messageId()),
              t.timestamp(), t.rawEvent())
        : e).toList();
}
```

代价：全量 JSON 随 Msg metadata **持久化进 state 文件**（磁盘膨胀至 compaction）；多一个全局 bean。适用：想保留 content=摘要的干净语义时。**默认选方案一**。

### 3.4 不建议的路径（核实过不可行）

| 路径 | 为什么不行 |
|---|---|
| 只用 `@Tool(converter=...)` 每工具转换 | converter 产物同时喂 SSE 与 memory，无法分离（`ToolResultConverter.convert` 输出即最终 block）；且反射实例化、无 Spring DI |
| 指望 metadata 默认透传到 SSE | 内置 `ToolResultEventConverter` 完全不读 metadata；官方示例注释提到的 `ToolResultBlockConverter` **类不存在**（jar 与官方仓库双向核实，示例注释泛称） |

### 3.5 错误形态（前端渲染错误态的依据）

- 工具抛异常 → `ToolResultBlock.error("Tool execution failed: <msg>")`（state=ERROR）→ SSE 照常发 `TOOL_CALL_RESULT`（content=错误文本）。**`AguiEvent$ToolCallResult` 无 state/error 字段**，前端只能靠 content 嗅探（现有 `ToolCallCard` 的 `/error/i` 正则即此模式，图表卡沿用并扩展 `"Tool execution failed"` 关键词）。
- `RUN_ERROR` 是流级错误（模型/adapter 层），对已挂卡片无影响——没有 toolMessage 就不 complete，卡片停在 inProgress；错误横幅走现有 `onRunErrorEvent` 订阅（ThreadArea 已有）。

## 四、前端 CopilotKit 层（渲染器体系）

### 4.1 useRenderTool 事实清单（1.70.1 本地 .d.mts 核实）

| 事实 | 内容 |
|---|---|
| 签名 | `{name, parameters(zod 必填), render, agentId?}`；**无 handler、无 followUp**（"This hook only handles rendering"） |
| render props | `{name, toolCallId, parameters, status, result}` 三态判别联合：inProgress（`Partial<T>`）/ executing（完整 T）/ complete（完整 T + `result: string`） |
| `parameters` | 恒为 `partialJSONParse` 产物（对象），流式期间部分字段缺失；渲染路径**不做 zod 校验** |
| `result` | **仅在 complete 有值且是 string**（toolMessage.content 原文）——渲染器自行 `JSON.parse` |
| 匹配优先级 | 精确名（agentId 匹配 > 无 agentId > 任意）→ 通配 `*`；同名后注册覆盖；卸载**不注销**（历史消息仍可渲染） |
| agentId | headless 无 ChatConfigurationProvider → 查询值恒 `"default"`，**新渲染器不传 agentId** |
| 错误 | 无 isError/error 字段；错误在 result 字符串内容里（§3.5） |
| executing 态 | 仅前端工具触发；本仓库全后端工具 → 实际只有 inProgress→complete 两态 |

### 4.2 前置必修：toolMessage 配对（现状缺陷）

`ThreadArea.tsx:212` 现在是 `renderToolCall({ toolCall: tc })`——没传 toolMessage。后果：后端工具卡片**永远 inProgress、result 恒 undefined**（complete 依赖 toolMessage 配对）。修法（官方 `CopilotChatToolCallsView` 范式）：

```tsx
// ThreadArea.tsx AssistantMessage 内（memo 组件需把 messages 或 Map 传进来）
const renderToolCall = useRenderToolCall();
const toolMessageByCallId = useMemo(
  () => new Map(messages.filter(m => m.role === "tool" && m.toolCallId).map(m => [m.toolCallId!, m])),
  [messages]);
// 渲染：
{message.toolCalls.map(tc =>
  renderToolCall({ toolCall: tc, toolMessage: toolMessageByCallId.get(tc.id) }))}
```

这是图表渲染器的**前置依赖**（拿不到 result 就没有数据）；配套单测不能再 mock 掉 renderToolCall 来回避。

### 4.4 ECharts 按需引入与 hook（官方文档核实）

`lib/echarts-setup.ts`（模块清单逐一核对自 echarts@6.1.0 `lib/export/*.js`）：

```ts
import * as echarts from "echarts/core";
import { PieChart, BarChart, LineChart, CandlestickChart } from "echarts/charts";
import {
  TooltipComponent, GridComponent, LegendComponent, TitleComponent, DatasetComponent,
  DataZoomComponent,   // = Inside + Slider（install.js 核实；仅 inside 可用 DataZoomInsideComponent）
} from "echarts/components";
import { LabelLayout, UniversalTransition } from "echarts/features";
import { CanvasRenderer } from "echarts/renderers";

echarts.use([PieChart, BarChart, LineChart, CandlestickChart,
  TooltipComponent, GridComponent, LegendComponent, TitleComponent, DatasetComponent,
  DataZoomComponent, LabelLayout, UniversalTransition, CanvasRenderer]);
```

**树摇守卫（必做）**：ESLint `no-restricted-imports` 禁裸 `'echarts'` 入口（一处全量 import 即把 379KB gzip 全拉回包，实测 218→379KB），只放行 `echarts/core|charts|components|features|renderers` 与 `import type`。

`useECharts.ts`（自写 hook，替代 echarts-for-react——其 Next.js 需 `transpilePackages`、双 init 反模式、3.x 发布线 2026-05 出现撤包）：

```tsx
"use client";
import { useEffect, useRef } from "react";
import { init, type EChartsType } from "echarts/core";
import type { ECOption } from "@/lib/echarts-setup";
import { currentThemeName } from "@/lib/chart-theme";

export function useECharts(option: ECOption | null) {
  const ref = useRef<HTMLDivElement>(null);
  const chartRef = useRef<EChartsType | null>(null);
  useEffect(() => {
    const el = ref.current; if (!el) return;
    const chart = init(el, currentThemeName());            // init 只在 effect（SSR 无 DOM）
    chartRef.current = chart;
    const ro = new ResizeObserver(() => chart.resize());
    ro.observe(el);
    return () => { ro.disconnect(); chart.dispose(); chartRef.current = null; }; // StrictMode 对称清理
  }, []);
  useEffect(() => { if (option) chartRef.current?.setOption(option, { notMerge: true }); },
    [option]);                                              // notMerge：系列增减不留残影
  return { ref, chart: chartRef };
}
```

主题对接（`chart-theme.ts`）：ECharts 主题值**不能写 `var(--x)`**，需 `getComputedStyle(document.documentElement)` 解析成实际色值（在 effect/首次渲染时执行，勿在模块顶层触 window）；模块内 `registerTheme("app-dark"/"app-light", {...})` 预注册两个主题，映射 `--color-panel`（背景）/`--color-line`（轴线）/`--color-ink{,-dim,-faint}`（文字）/`--color-accent`（强调）/`--color-up`红/`--color-down`绿（涨跌）。v6 支持 `chart.setTheme()` 动态切换免重建（暗/亮切换时用）。

### 4.6 ChartCard 状态机壳

```tsx
"use client";
export function ChartCard({ status, result, parameters, builder }: RenderProps) {
  if (status !== "complete" || result == null)
    return <div className="tool-card running">{/* 参数骨架：沿用 ToolCallCard 进度样式 */}</div>;
  const parsed = safeJsonParse(result);                     // 容错：解析失败降级折叠 JSON
  const check = ChartSpecSchema.safeParse(parsed);          // 单一契约：table 是变体之一（2026-09-11 澄清）
  if (!check.success || isToolError(result))                // §3.5 错误嗅探："Tool execution failed"
    return <details className="tool-card"><summary>数据异常（原始结果折叠）</summary><pre>{result.slice(0, 2000)}</pre></details>;
  const spec = check.data;
  return spec.type === "table" ? <DataTable spec={spec} />  // 按变体分发，无需独立 schema/table prop
                               : <EChart option={builder(spec, currentPalette())} />;
}
```

要点：option 必须 `useMemo`（每次 render 新建整棵 option 字面量会废掉 setOption 的 merge 优化）；卡片外壳复用 `.tool-card` 类与 CSS 变量（与 InterruptApprovalCard 同套视觉）。

### 4.7 大数据交互表（TanStack Table v9）

⚠ **latest 已是 v9.2.4**（2026-08-04 转正；v8 止于 8.21.3）——网上资料多为 v8，API 有代差：`useReactTable` → `useTable` + `tableFeatures`；`getSortedRowModel()` → `sortedRowModel: createSortedRowModel()`。

```tsx
"use client";
import { useTable, tableFeatures, rowSortingFeature, createSortedRowModel,
         sortFn_alphanumeric, sortFn_datetime, flexRender } from "@tanstack/react-table";

const features = tableFeatures({
  rowSortingFeature,
  sortedRowModel: createSortedRowModel(),
  sortFns: { alphanumeric: sortFn_alphanumeric, datetime: sortFn_datetime },  // 只注册用到的（树摇）
});

export function DataTable({ spec }: { spec: TableSpec }) {
  const columns = useMemo(() => spec.columns.map(c => ({
    id: c.key, header: c.label, accessorKey: c.key, size: c.align === "right" ? 96 : 120,
    sortFn: c.sortable === false ? undefined : "alphanumeric",
  })), [spec]);
  const table = useTable({ features, columns, data: spec.rows });
  return (
    <div className="max-h-[360px] overflow-auto rounded-md border border-[color:var(--color-line-soft)]">
      <table className="w-full text-xs">
        <thead><tr>{table.getHeaderGroups()[0].headers.map(h => (
          <th key={h.id} onClick={h.column.getToggleSortingHandler()}
              className="sticky top-0 z-10 bg-[color:var(--color-panel-2)]"
              style={{ width: h.column.getSize(), textAlign: spec.alignOf(h.id) }}>
            {flexRender(h.column.columnDef.header, h.getContext())}
            {{ asc: " ▲", desc: " ▼" }[h.column.getIsSorted() as string] ?? ""}
          </th>))}</tr></thead>
        <tbody>{table.getRowModel().rows.map(r => (
          <tr key={r.id}>{r.getVisibleCells().map(c => (
            <td key={c.id} className="px-2 py-1">{flexRender(c.column.columnDef.cell, c.getContext())}</td>))}
          </tr>))}</tbody>
      </table>
    </div>
  );
}
```

固定表头 = 原生 `position: sticky` CSS（TanStack headless 无 sticky API，官方哲学是样式自写）；**本期不装 react-virtual**（官方原话 "For small tables, normal rendering is simpler"），行数上千时再按官方 Virtualization 指南接 `useVirtualizer`（届时表格布局要切 `display:grid` 模式）。注意 v9 方法挂原型，**不可解构**（`const {getValue} = row` 丢 this）。

## 五、新增依赖与体积

### 5.1 recharts → ECharts 全站替换评估（2026-09-10，已确认）

**结论：可以且建议全部替换。** 依据：

1. **使用面极窄且零高级特性**：recharts 3.10.1 仅 4 个组件使用（AllocationPie 环形图、IndustryBar/DeviationChart 柱状、TrendChart 折线），无 formatter/ReferenceLine/Brush/自定义动画——全部是 ECharts 基础能力一对一映射（`Pie+Cell`→data 项级 `itemStyle`、`CartesianGrid`→`splitLine`、`ResponsiveContainer`→useECharts 的 ResizeObserver）。
2. **体积净省 ~126KB gzip（-36%）**：双库并存 = recharts 用到子集 **126KB**（esbuild+gzip 实测，与 ECharts 同方法）+ echarts 按需 **218KB** = 344KB；单库 ECharts = 218KB（pie/bar/line 本就在聊天流按需注册集内）。
3. **复用红利**：4 个组件恰好是 pie/bar/line——本方案 `optionBuilders` 直接复用，页面组件退化为「数据→ChartSpec→EChart」薄壳（每组件 ~30 行）。
4. **测试模式零跨越**：现有 13 个用例（AllocationPie 3 + IndustryBar 3 + TrendChart 5 + DeviationChart 2）本来就完全 mock recharts（断言数据映射非 SVG 结构）——迁移后改断言 option builder 输出，与 §六 同一模式。

风险：视觉回归一轮 QA（canvas vs SVG、ECharts v6 legend 默认在底部）；`ResponsiveContainer` 隐式撑高 → 显式容器高度（现状组件已写死 height，直接平移）。**手写 SVG 的 `market/KlineChart.tsx`（非 recharts，自定义十字线）不在本次范围**，是否收敛到 `buildCandlestickOption` 另议。

### 5.2 依赖清单

| 包 | 版本 | 体积 | 说明 |
