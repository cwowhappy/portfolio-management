# 数据采集服务（collector）系统架构与技术方案

- 日期：2026-08-28
- 状态：已实现（降级已落地；速率控制部分为方案，见 §四）
- 相关：[V3 估值表 DDL](../../../backend/src/main/resources/db/migration/V3__valuation.sql) · [市场估值需求规格说明](../../../features/market-valuation/01-requirement/需求规格说明.md) · [ADR-0003 行情数据源](../decisions/0003-market-data-source.md)

## 一、背景与目标

「市场估值」特性需要每日收盘后产出全市场估值快照。区别于 Java 后端的实时行情（ADR-0003：东财主源 + 新浪/腾讯兜底 + 令牌桶限流 + TTL 缓存），采集侧是一次性的、批量的、日频的数据工程任务。因此独立为一个 **Python 服务 `collector/`**，用 akshare + tushare 接数据源、pandas 计算、psycopg 落库，APScheduler 调度。

目标：每日收盘后（工作日 15:30）自动产出并持久化全市场估值快照，**只写不建**（零 DDL），把数据写入 Java 后端（P1）用 Flyway 定义的表。

## 二、总体架构

```
collector/（Python 3.12，独立服务）
  config.py            env：DATABASE_URL / TUSHARE_TOKEN
  sources/             akshare + tushare adapter（归一化列名）
    universe.py          全 A 股估值（akshare，免费）
    treasury.py          10 年国债收益率（akshare，免费）
    index.py             指数每日估值（tushare，需 token）
    industry.py          申万行业映射（tushare index_classify + index_member_all）
  calc/                pandas 纯计算
    snapshot.py          全A PE/PB 中位数（剔除 PE≤0/PE>100）、破净占比、申万行业市值加权
  store/               psycopg 幂等 upsert（ON CONFLICT DO UPDATE，零 DDL）
  backfill.py          指数历史回填 runner（一次性，非每日）
  scheduler/jobs.py    APScheduler（BlockingScheduler，工作日 15:30，coalesce，3× 重试）
  run_once.py          一次性编排 collect_once（手工触发 make collect）
        │  写入（零 DDL）
        ▼
PostgreSQL（Flyway V3 五表，schema 单一源头，由 Java 后端拥有）
  valuation_snapshot / treasury_yield / index_valuation_history /
  industry_valuation / shenwan_industry_mapping
```

**关键原则**：

- **采集（写）与查询（读）分离**：collector 只负责数据写入，读侧（`/api/valuation/**` 查询、AI 工具）由 Java 后端完成，二者共享 PostgreSQL。
- **schema 单一源头**：表结构与列类型由 Flyway（Java）定义，collector 只 INSERT/UPDATE，逐字对齐 V3 列名（跨服务契约）。
- **分层清晰**：`sources`（归一化列名）→ `calc`（纯计算）→ `store`（幂等落库），adapter 不 import calc/store，calc 不碰网络/DB。

## 三、数据源矩阵与多级降级

### 3.1 数据源矩阵

| 数据 | 来源（函数） | 是否需 token | 降级地位 | 备注 |
|---|---|---|---|---|
| 全 A 股估值快照 | akshare `stock_zh_a_spot_em`（东财批量） | 否 | **基础层** | ~5000 只，内部 19 页分页 |
| 10 年期国债收益率 | akshare `bond_zh_us_rate` | 否 | **基础层** | 按日期倒序取最新 |
| 指数每日估值 | tushare `index_dailybasic` | 是 | 增强层 | 仅返回 pe/pb，**无股息率** |
| 申万行业映射 | tushare `index_classify` + `index_member_all` | 是（2000 积分） | 增强层 | 31 一级行业，`.SI` 后缀 |
| 指数历史回填 | tushare `index_dailybasic`（近 10 年） | 是 | 一次性 | 独立 runner，非每日 |

### 3.2 降级策略（已实现）

**分层降级 + 失败隔离**：`collect_once` 把免费数据（akshare）与付费数据（tushare）解耦，**免费数据先落库**，tushare 依赖段失败不回滚已落库数据。

```
1) akshare 全 A 估值 + 国债（免费，无 token）
2) upsert 快照 + 国债   ← 先落库（基础层保底）
3) tushare 段（try/except 隔离）：
   3a) 每日指数估值（5 指数）
   3b) 申万行业映射（31 次 index_member_all）
   3c) 行业加权估值 + 映射落库
   失败 → logger.exception("tushare 段失败，降级为仅快照+国债")，继续
```

- **基础层保底**：只要 akshare 可用，市场快照 + 国债就落库，市场估值仪表盘的核心指标（全 A 中位数/破净/ERP 输入）不中断。
- **增强层降级**：tushare 鉴权/限流/权限不足（如 2000 积分不满足）时，指数估值、申万行业、行业加权三类数据缺省，读侧以「数据积累中」/空值降级展示。
- **整管重试**：`scheduler/jobs.py` 对整条 `collect_once` 做 3 次重试（间隔 30s），兜住瞬时故障（如东财偶发断连）。

### 3.3 降级缺口（当前局限）

1. **akshare 段无 try/except 隔离**：东财批量接口偶发 `ServerDisconnectedError` 时，`collect_once` 在基础层即中止，仅靠 `jobs.py` 的整管 3× 重试兜底（手工 `run_once` 无重试）。
2. **同类型无多供应商兜底**：与 Java 后端（ADR-0003 的东财主源 + 新浪/腾讯兜底）不同，collector 每个数据类型只有单一来源——universe/国债仅 akshare，指数/申万仅 tushare，无「换源降级」。
3. **ERP 股息率无数据源**：`index_dailybasic` 不返回股息率（`dividend_yield` 置 None），沪深 300 股息率需另接中证指数公司 / akshare 乐咕乐股，否则股债利差（ERP）一直「积累中」。

## 四、接口访问速率控制

### 4.1 现状

collector **未实现客户端限速器**（区别于 Java 后端的令牌桶 `RateLimiter` 5 req/s + `TtlCache`）。当前依赖：

- **tushare 服务端限流**：tushare.pro 按积分等级对接口做服务端限流（免费/低积分账户频率受限）。
- **akshare 内部分页**：`stock_zh_a_spot_em` 自行分页请求东财批量接口，collector 侧无额外控制。
- **固定间隔重试**：`jobs.py` 3× 重试，固定 30s，无指数退避。

### 4.2 风险

| 风险 | 影响 | 建议 |
|---|---|---|
| 申万映射每日 31 次 `index_member_all` | 日频重复拉取近乎静态的行业成分，浪费 quota、放大限流暴露 | 按 FR-A2「定期更新机制」**每周缓存**一次，映射表可复用 |
| 指数历史回填逐行 commit（近 10 年 × 5 指数 ≈ 1.2 万次） | 单事务开销大、易触发限流/超时 | 改为 `executemany` 批量 + 单事务提交 |
| 固定 30s 重试无退避 | 上游持续限流时反复撞限 | 改指数退避（如 30s/60s/120s） |
| 无客户端限速 | 突发 31 连发 `index_member_all` 可能触发 tushare 限流 | 加简单令牌桶或调用间隔（如 0.5s/次） |

### 4.3 技术方案（建议，未实现）

按优先级：

1. **申万映射周级缓存**（高优先，收益最大）：把 `fetch_shenwan_mapping` 结果落库后，日任务只在映射表为空或超过 7 天时重拉，其余直接复用，从「每日 31 连发」降到「每周一次」。
2. **回填批量化**（高优先）：`backfill_index_history` 用 `executemany` 单事务，替换逐行 `upsert_index`。
3. **轻量限速**（中优先）：在 tushare 调用循环（`index_member_all` 31 次）间加固定间隔（如 0.5s）或简单令牌桶；不引入重依赖。
4. **指数退避重试**（中优先）：`jobs.py` 的 `RETRY_DELAY` 由固定 30s 改为 30s/60s/120s 退避。
5. **akshare 段隔离 + 换源兜底**（低优先，视稳定性）：给 akshare 段也加 try/except 日志；如东财批量接口频繁抖动，可评估接入新浪/腾讯批量兜底（对齐 ADR-0003 的多源思路）。

## 五、部署与可观测性

- **部署**：`collector/Dockerfile`（python:3.12-slim）+ `docker-compose.yml` 的 `collector` 服务；`depends_on backend: service_healthy`（等 Flyway 建表）+ `db`；`TZ=Asia/Shanghai`；`TUSHARE_TOKEN` 经环境变量透传（`.env` git-ignored）。
- **调度**：APScheduler `CronTrigger(mon-fri 15:30)` + `coalesce=True`（避免积压）。
- **可观测性**：`logging.basicConfig` + `logger.exception`（各阶段失败有日志）；`make collect`（手工触发一次）、`make collect-test`（pytest，覆盖率 ≥80%）。
- **已知缺口**：无结构化指标/告警（仅日志）；容器 `python:3.12-slim` 需补装 `tzdata` 才能让 `TZ=Asia/Shanghai` 真正生效；未接入交易日历（中国节假日仍会跑）。

## 附：与 Java 后端行情链路的对比

| 维度 | Java 后端（ADR-0003） | collector（本文档） |
|---|---|---|
| 数据源降级 | 东财主源 + 新浪/腾讯兜底（同类型多供应商） | 单一来源，仅「akshare→tushare」分层降级 |
| 速率控制 | 令牌桶 5 req/s + TTL 缓存 | 无客户端限速，依赖服务端限流 + 整管重试 |
| 缓存 | TtlCache（行情热缓存） | 无（映射表建议周级缓存，见 §4.3） |
| 定位 | 实时、低频量、面向在线查询 | 批量、日频、面向离线快照 |
