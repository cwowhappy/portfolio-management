# 测试驱动开发 (Test-Driven Development)

## 概览

TDD 把「先想清楚要什么行为，再动手写实现」变成可执行的纪律：**先写一个会失败的测试，再写让它通过的最小代码，最后重构**。本 skill 覆盖两个阶段：

1. **编写开发计划** —— 把需求拆成可逐条验证的测试清单，再映射为实现步骤
2. **执行开发计划** —— 按 Red-Green-Refactor 循环逐条实现，在决策点暂停确认

## 何时用哪条流程

```
有需求，但还没想清楚怎么实现？          → 流程 A：编写开发计划
已有计划（本 skill 或他人产出），要落地？ → 流程 B：执行开发计划
改动极小、行为一目了然？               → 直接跑下面的核心循环，无需完整计划
```

## 核心：Red-Green-Refactor 循环

```
┌─────────┐    ┌──────────┐    ┌──────────┐
│  RED     │───▶│  GREEN   │───▶│ REFACTOR │──┐
│ 写失败测试 │    │ 最小实现   │    │  去重/优化 │  │
└─────────┘    └──────────┘    └──────────┘  │
     ▲                                        │
     └────────────── 测试始终绿 ────────────────┘
```

**RED** —— 写一个会失败的测试，精确描述想要的行为。**必须实际运行并看到它失败**，且失败原因正确（是断言失败，而不是编译错误/找不到方法这类「错因」）。

**GREEN** —— 用最少代码让测试通过。允许「作弊」：硬编码返回值、复制粘贴。此时不追求设计，只求测试尽快变绿。

**REFACTOR** —— 消除重复、改善结构，**不改变行为**。每次重构后立刻跑测试确认仍绿。

### 三条实现策略（依次优先）

1. **Fake it（先造假）**：直接返回常量让测试通过，后续测试逼出真正的逻辑
2. **Triangulation（三角定位）**：写两个不同示例逼出通用实现（对不确定的算法尤其有用）
3. **Obvious implementation（显然实现）**：实现路径足够直白时直接写，不必绕弯

### 铁律

- **一次只做一件事**：要么写测试，要么写实现，要么重构，三者不混
- **测试行为，不测试实现**：断言「做什么」，不断言「怎么做」；重构不应破坏测试
- **每个测试只验证一个行为**：失败时能一眼定位原因
- **Arrange-Act-Assert**：三段式结构（准备 → 执行 → 断言）
- **FIRST**：Fast（快）/ Independent（独立，不依赖执行顺序）/ Repeatable（可重复）/ Self-validating（自校验）/ Timely（及时，实现前先写）

## 流程 A：编写开发计划

1. **澄清需求**：把需求转成可观察的行为。对每条规则问「给定什么输入，期望什么输出/副作用？」。明确边界条件（空值、0、负值、越界、异常）。**需求含糊处先问用户**，不要替用户猜。
2. **拆解测试清单**：为每个行为写一条测试意图。测试名用行为描述（如 `returns total with tax`、`should return 0 when list is empty`），不要用 `testMethod1` 这种无意义命名。
3. **排序**：从最简单、无依赖的用例开始；复杂/边界用例靠后，排成可逐个攻克的顺序。
4. **规划实现步骤**：每条测试对应一个 RED→GREEN→REFACTOR 步骤，标注要创建/修改的文件路径（含测试文件）。
5. **产出计划**：用 `assets/plan-template.md` 模板写计划文档，保存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`（与项目现有约定一致）。

测试清单的质量门槛见下方「测试清单规则」。

## 流程 B：执行开发计划

1. **载入并评审计划**：读计划文件，批判性检查——测试是否真能驱动实现、步骤是否自洽、文件路径是否正确。**有疑虑先提出，不要硬执行**。
2. **建 TODO 列表**：把计划的每个测试步骤建成 TodoWrite 项，逐条推进。
3. **逐条 Red-Green-Refactor**：对每条测试严格按循环执行——先写失败测试并确认红 → 写最小实现并确认绿 → 需要时重构。**每完成一条，运行整个测试套件**确认无回归。
4. **检查点暂停**：遇到下列情况停下询问，而非自行决定（详见下节）。
5. **汇报**：每完成一批（默认 3 条测试）或到达检查点，展示已实现内容 + 测试运行结果，等用户反馈再继续。

## 检查点：何时暂停并询问

- **需求含糊**：无法从需求确定某个行为的期望结果
- **公共接口设计**：函数签名/类名/模块边界的形状会影响下游，需要拍板
- **范围蔓延**：实现中发现计划之外的新行为
- **设计受阻**：让测试通过需要明显超出「最小实现」的结构性改动（说明该行为需要更大重构，应回到计划）
- **测试反复失败**：同一测试多次无法转绿，说明对行为理解有误或存在环境/依赖问题

**原则：宁可停下来问，也不要硬猜着写。**

## 测试清单规则

- 一条 = 一个可独立验证的行为/规则，而不是一个「方法」
- 测试名自解释（读名即知行为）
- 覆盖：正常路径 + 边界（空/0/负/越界）+ 异常/错误路径
- 按「从简到繁、从无依赖到有依赖」排序
- 实现过程中想到新测试，随时补进清单；清单清空即完成
